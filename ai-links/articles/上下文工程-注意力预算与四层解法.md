# 上下文工程：为什么窗口越大模型越蠢

See also: [[AI-Links-KB-Home]] | [[Articles-Index]] | [[上下文工程落地实践-从理论到Claude-Code实现]] | [[Claude-Code记忆机制源码拆解]] | [[AI大模型开发]]

## 摘要

Transformer 的注意力是有限且需要分配的——context 每多一个 token，真正关键信息的注意力份额就被稀释一分。这是「窗口 100 万但回答更蠢」的根源，由此衍生三个具体现象：**注意力稀释**（噪声淹没信号）、**Lost in the Middle**（context 中间段信息命中率断崖下跌，呈 U 形曲线）、**Context Rot**（长 Agent 轨迹中过期矛盾信息堆积，模型反刍自己制造的垃圾）。〔2026-09-13 术语更正：Context Rot 的准确定义是「输入 token 增长导致召回能力下降」；「轨迹中过期矛盾信息堆积」属 Drew Breunig 归纳的 Context Poisoning / Clash——详见 2.3 节更正块。〕

工程解法四层叠加：**检索**（只放相关片段，性价比最高）、**压缩**（长轨迹摘要，留结论留约束留待办，扔过程噪声）、**子 Agent 隔离**（独立 context 互不污染）、**渐进式披露**（Skills 式按需分级加载）。核心原则：**哪怕窗口有 100 万 token，也要像只有 8000 一样经营 context——永远只放信号，不放噪声。** 有效上下文 > 最大上下文。

## 一、核心认知：Context 不是仓库，是注意力预算

Transformer 每生成一个 token，都要在所有已有 token 上做注意力计算。注意力的总量是有限的，在所有 token 之间**此消彼长竞争**。

> [!quote] 一手出处（Anthropic《Effective context engineering for AI agents》，2025-09-29）
> "Context, therefore, must be treated as a finite resource with diminishing marginal returns. Like humans, who have limited working memory capacity, LLMs have an "attention budget" that they draw on when parsing large volumes of context. Every new token introduced depletes this budget by some amount…"
> 机制段原文："LLMs are based on the transformer architecture, which enables every token to attend to every other token across the entire context. This results in n² pairwise relationships for n tokens."
> 来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
> 边界：Anthropic 的 "Like humans…" 是解释用的心智模型（mental model），**不是**被测量出的注意力分配定律；「注意力预算」目前没有逐 token 的定量测量支撑。

> [!warning] 机制精确化（2026-09-13）：「注意力总量有限 / 在所有 token 之间此消彼长竞争」是**类比**，机制上更严谨的三点是——
> - softmax 使**单个 query** 的注意力权重在全部 key 上归一化到 1（就这一个 query 而言确实是零和的）；
> - 但模型有**多个 head、多层，且每步一个 query**，它们并不共享一个可耗尽的全局预算；
> - 「窗口越大越蠢」的可观测成因主要是**位置偏差**（causal masking 与 RoPE 等结构因素）、**干扰项竞争**与**训练分布不匹配**，而不是某个池子被抽干。
> - 来源：[agentpatterns-ai — lost-in-the-middle](https://raw.githubusercontent.com/agentpatterns-ai/website/refs/heads/main/context-engineering/lost-in-the-middle.md)

| Context 长度 | 每条关键信息分到的注意力 |
|-------------|---------------------|
| 1000 token | 充裕 |
| 50 万 token | 被几十万个不相关 token 稀释到几乎可忽略 |

> [!warning] 更正（2026-09-13）：上表两档对照是定性类比，未找到任何一手来源给出这个量化结论（原表述保留以便追溯）。Chroma 技术报告《Context Rot: How Increasing Input Tokens Impacts LLM Performance》(2025-07-14) 的实测结论是：退化幅度与模型、任务类型、干扰项、needle 与问题的语义相似度都相关，各模型曲线差异明显——例如 Gemini 2.5 Pro 在 50 词这种极短输入上起点就偏低，GPT-4.1 约从 2500 词开始出现拒绝回答（2.55%），Qwen3-8B 有 4.21% 的非尝试率。可核实的替代表述：**「随 token 增长，关键信息的可召回性下降，且模型与任务间差异显著」**。
> 来源：https://www.trychroma.com/research/context-rot

类比：context window 是会议室的桌子，不是隔壁的档案室。档案室能放一万份文件（训练知识 + 外部知识库），但会议桌上真正摊开讨论的只能是有限的几份。全堆上去的结果不是「信息更全」，而是「谁也找不到要讨论的那份」。

## 二、三个具体现象

### 2.1 注意力稀释

塞满 100 万 token ≠ 这 100 万 token 都在为当前回答出力。大量 token 只是在**互相干扰**。一条明明在 context 里的信息被记错——不是模型没「存」住，是它的注意力权重被几千条噪声冲没了。

### 2.2 Lost in the Middle（中间盲区）

斯坦福研究：同一条关键信息分别放在长文档的**开头、中间、结尾**，问相关问题。结果呈 U 形曲线：

| 信息位置 | 答对率 |
|---------|--------|
| 最开头 | 最高 |
| 最结尾 | 次高 |
| 正中间 | 断崖式下跌，部分设置下接近「根本没给这条信息」 |

模型读长 context 跟人考前抱佛脚一样——首因效应 + 近因效应，记头记尾，中间大段划水。

**工程杀伤力**：彻底否定「窗口大就按文档原始顺序一股脑灌」。文档物理顺序和信息重要性是两件无关的事。重要信息落在中间区 = 等于没放。

> [!warning] 补两条限定（2026-09-13）：「重要信息落在中间区 = 等于没放」会过度泛化，可核来源给出两条边界——
> - **输入只有几百 token 时不存在有意义的「中间区」**（"When the whole input fits in a few hundred tokens, there is no meaningful middle zone"）：短 context 场景不必按位置焦虑；
> - **位置偏差不是所有模型的宿命**：经过长上下文微调或指令跟随强化的模型，中间退化更小——"treat placement as a default safeguard, not a guarantee"。
> - 机制归属：该页把位置偏差追溯到**结构性因素**（causal masking 与 RoPE 等相对位置编码），并强调 "This is a structural property…not a quirk of any particular model"；同页给出 Liu et al., 2023 (arXiv:2307.03172) 与 Hsieh et al., 2024 (arXiv:2406.16008, RULER) 两个编号。
> - 来源：[agentpatterns-ai — lost-in-the-middle](https://raw.githubusercontent.com/agentpatterns-ai/website/refs/heads/main/context-engineering/lost-in-the-middle.md)

**实测案例**（金融保险 RAG 项目）：检索回 20 个 chunk 按相似度顺拼，Top1 chunk 命中了答案但模型用了排第 8 的错误 chunk。原因——最关键的几个 chunk 挤在 context 中段盲区。改为最相关 chunk 放首尾、次要放中间，同一套检索结果，答案正确率直接抬一截。

> [!warning] 更正（2026-09-13）：该「实测案例」的唯一来源是本页 frontmatter 登记的微信公众号转载（该链接本次抓取被重定向到「环境异常」验证页，无法直读），既无项目名、无评测集，也无量化结果（「抬一截」无从核实）——**不得当作可引用的实验证据**，请按「来源文章自述、未经独立核实」对待（原表述保留以便追溯）。「关键信息放首尾、别落在中段」的真正依据是 Liu et al.《Lost in the Middle: How Language Models Use Long Contexts》（arXiv:2307.03172，该文为学界公认出处；本次 arXiv 站点不可达，未逐字复核页面），它同时支撑本节上面的 U 形曲线说法。可替代的公开证据（2026-09-13 补）：Liu et al. 2023（位置效应）与 RULER（Hsieh et al., 2024, arXiv:2406.16008，长上下文评测基准——该编号由上述可核来源页给出）。

### 2.3 Context Rot（上下文腐烂）

长 Agent 轨迹（几十步 tool call）中堆积大量过期、矛盾、自我引用的内容，模型输出持续退化且「越陷越深」。

根源：过期信息占用注意力预算（稀释），且这些信息体量大、反复出现，权重不降反升（位置/频次）。

> [!warning] 更正（2026-09-13）：本节原表述把两件不同的事并成了一个术语，且「权重不降反升（位置/频次）」找不到出处（原表述保留以便追溯）。正确的拆分是：
> ① **Context Rot = 长度导致的召回退化**。它是 Chroma 技术报告《Context Rot: How Increasing Input Tokens Impacts LLM Performance》(2025-07-14) 的标题概念：随输入 token 增长，模型从上下文中**准确召回**信息的能力下降，在简单任务上也会出现。Anthropic 即按这个定义引用它——"Studies on needle-in-a-haystack style benchmarking have uncovered the concept of context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases."
> 来源：https://www.trychroma.com/research/context-rot ，https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
> 出处补全（2026-09-13）：Chroma 报告署名为 **Kelly Hong、Anton Troynikov、Jeff Huber**（2025-07），报告评估 **18 款主流 LLM**，核心命题是「输入长度增加本身就会导致性能下降，与任务复杂度无关」；中文转述见 [澎湃号·湃客《上下文腐烂：当百万 token 成为 AI 模型的阿喀琉斯之踵》（2025-08-29）](https://m.thepaper.cn/newsDetail_forward_31500760)，该文确认了术语出处与作者。
> ② **「轨迹里过期、矛盾、自我引用的内容堆积 → 模型反复引用错误」是另一组失效模式**，出自 Drew Breunig《How Long Contexts Fail》(2025-06-22) 归纳的 Context Poisoning / Context Distraction / Context Confusion / Context Clash（Simon Willison 2025-06-29 链接博文逐条转述，已抓取核对原文）。下文「方案 A 失败、方案 B 失败、第 30 步还在重复」的例子正确归属是**这一组**（Poisoning / Clash），不是 Context Rot。
> 来源：https://simonwillison.net/2025/Jun/29/how-to-fix-your-context/
> ③ 机制侧：Anthropic 给的是 n² 成对关系被拉薄、训练分布中短序列更常见、位置编码插值造成 token 位置理解退化，并明确结论是**性能渐变而非断崖**，没有「权重不降反升」的说法；Chroma 报告在正文明确把注意力层面的机制列为范围之外，只给任务级指标。可核实的替代表述：**「反复出现的过期内容会持续占用 token 预算，并提高模型再次复述它的概率」**。

典型场景：Agent 前面试了方案 A 失败（全写进 context）、方案 B 也失败（全写进 context），走到第 30 步，context 里全是「我刚才搞砸了」的痕迹——模型不断重复已证明无效的思路（在 context 里反复出现，注意力权重高），或彻底迷失在一堆中间状态里。

关键认知：不能指望模型「更聪明地忽略垃圾」——没法跟概率模型讲「这段你别当真」。必须从工程上**阻止垃圾在 context 里堆积**。

## 三、四层工程解法（从轻到重，叠加使用）

| 层级 | 解法 | 原理 | 典型实现 |
|------|------|------|----------|
| 1 | **检索**（Retrieval） | 5000 份文档不灌，先检索出当前问题真正需要的 3-5 个片段 | RAG |
| 2 | **压缩**（Compaction） | 20 步探索过程 → 结构化进展摘要（做过什么、结论、卡在哪）→ 几百字替换几万 token 原始轨迹 | Claude Code context 自动压缩 |
| 3 | **子 Agent 隔离** | 大任务拆给多子 Agent，各自独立干净 context，只把结论回传主线 | 多 Agent 架构 |
| 4 | **渐进式披露** | 第一级只放一句话元信息（让模型知道有这个能力），真正用时才加载第二级完整说明，需要文件才读第三级 | Claude Skills 分级加载 |

### 3.1 检索——性价比最高的第一步

RAG 的深层价值不只是「让模型访问外部知识」，更是**「让模型不必访问无关知识」**。把 100 万 token 噪声压成几千 token 信号。

### 3.2 压缩——长了就缩

不能简单砍掉最早几步（可能砍掉关键约束）。压缩的艺术：**留结论、留约束、留待办，扔掉过程噪声**。

Anthropic 的官方口径（逐字）："Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary." 并给出迭代顺序——**先保召回，再提精确率**："Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision by eliminating superfluous content."
判据：压缩后先跑「关键约束是否还在」的检查（召回），再删冗余（精确率）。
来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### 3.3 子 Agent 隔离——分而治之

表面是「分工」，底层是「context 隔离」。子 Agent 干完活只回传结论，中间探索过程烂在自己 context 里，不污染主线。

官方给出的量级：子 Agent 可以烧掉数万 token 去探索，但只回传 "often 1,000-2,000 tokens" 的蒸馏摘要——回传摘要的长度就是这一层的可验收指标（回传体积失控 = 隔离失效）。
来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### 3.4 渐进式披露——按需加载

Claude Skills 的核心设计。背后无论挂多少知识，任何时刻 context 里只有当前这一步真正用得上的部分。真实系统里四层叠用：检索取相关 → 压缩控长度 → 隔离防污染 → 渐进式减冗余。

官方把它叫 just-in-time 加载：**context 里只保留轻量标识符**（文件路径、查询语句、链接），运行时再用工具把数据取进来，而不是预先把数据塞进 context。
来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

### 3.5 结构化笔记 / 外部记忆（补齐的第五类官方手段）

前三层都在「context 内部做减法」，这一层是**把状态搬到 context 之外**：把进度写成文件（笔记、进度文件、看板），需要时再读回来。Anthropic 把它与「压缩」「多 Agent 架构」并列为长时程任务的三条核心手段（structured note-taking）。
选择建议（官方按任务类型给的取舍）：来回往复多的任务适合**压缩**；有明确里程碑、可迭代推进的任务适合**结构化笔记**——四层不是必须全部叠加。

## 边界与取舍（2026-09-13 补录）

前三节都在讲「越长越糟」，但一手来源比本文克制，落地前必须补上三条边界：

| 边界 | 内容 | 依据 |
|------|------|------|
| ① 是渐变，不是断崖 | 模型在长 context 下**仍然可用**，只是检索精度与长程推理相对下降——与本文标题级的「窗口越大模型越蠢」相比，来源的结论明显更保守 | Anthropic 原文："These factors create a performance gradient rather than a hard cliff: models remain highly capable at longer contexts but may show reduced precision for information retrieval and long-range reasoning compared to their performance on shorter contexts." |
| ② 目标不是「无条件最短」 | 官方目标是 "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome"；压缩与运行时探索（just-in-time）是两条需要权衡的路线，**不存在四层必须叠加**——压缩适合来回多的任务，结构化笔记适合有明确里程碑的迭代 | Anthropic 原文；见本文 3.2 / 3.5 |
| ③ 「长」不是唯一变量 | 干扰项增多、needle 与问题语义相似度下降都会掉分。Chroma 报告设有《Impact of Distractors》专节，并用高相似 needle-question 对做对照——**检索质量与长度是两个独立变量** | https://www.trychroma.com/research/context-rot |

可操作判据：**固定一套评测集，分别做两组对照——只压长度（其余不变）、只压干扰项/检索精度（长度不变），看哪一项对失败率的贡献更大**，再决定先投压缩还是先投检索。

## 四、核心原则

**有效上下文 > 最大上下文**。长窗口是双刃剑——它给了你「可以偷懒全塞进去」的能力，而这恰恰是大多数人翻车的根源。

成熟做法：哪怕有 100 万 token 窗口，也像只有 8000 token 一样经营 context。每放一段进去之前先问——**这段对当前这一步的回答，是信号还是噪声？**

## 五、面试应答框架

被问「为什么 context 越长模型表现反而下降」时：

1. **破误区（30s）**：上下文窗口不是仓库而是注意力预算。Transformer 注意力有限且竞争分配，context 越长 → 关键信息注意力份额被稀释 → 噪声淹没信号。

2. **位置效应（30s）**：Lost in the Middle。同一条信息放 context 首尾命中率高，放中间断崖下跌呈 U 形曲线。不能按文档原始顺序硬灌，最关键信息必须放首尾位置。

3. **长程退化（20s）**：Context Rot。多轮/长 Agent 轨迹中过期矛盾信息堆积，带着模型重复无效路径。

4. **工程解法（40s）**：四层叠加——检索只放相关片段、压缩做轨迹摘要、子 Agent 隔离独立 context、渐进式披露按需加载。核心原则：窗口 100 万也要像 8000 一样经营，只放信号不放噪声。

> [!tip] 补一句边界（2026-09-13）：面试里说「越长越蠢」容易被追问——准确说法是**性能渐变而非断崖**，且长度与检索质量是两个独立变量（见「边界与取舍」一节）。

> [!tip] 每段挂一条证据 + 一条边界（2026-09-13 补）：上面四段只给「说什么」，被追问时还需要「用什么兜」——
>
> | 断言 | 证据 | 边界（被追问时） |
> |---|---|---|
> | ① 注意力预算 | Anthropic《Effective context engineering for AI agents》原文 | 「预算」是心智模型、不是被测量的定律（见 §一 机制精确化） |
> | ② 位置效应 | Liu et al., 2023（arXiv:2307.03172） | 几百 token 内不存在有意义的中间区；长上下文微调 / 指令跟随强的模型中间退化更小（见 §2.2） |
> | ③ 长程退化 | Chroma《Context Rot》报告（18 款模型实测） | 是渐变不是断崖；长度与检索质量是两个独立变量（见「边界与取舍」） |
> | ④ 工程解法 | Anthropic 的 compaction / just-in-time / 子 Agent 回传 1,000–2,000 token 口径 | 不存在「四层必须全叠加」；压缩 vs 结构化笔记按任务类型取舍（见 §3.5） |
