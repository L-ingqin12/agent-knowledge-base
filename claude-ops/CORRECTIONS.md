# CORRECTIONS — 错误记忆库

See also: [[AGENTS]] | [[HOME]] | [[Claude-Ops-KB-Home]] | [[URL-Lookup]] | [[agent-memory-context-knowledge-design]] | [[DSH会话脱敏插件缺陷档案]] | [[DSH会话脱敏项目方法论复盘]]

> [!abstract] 这个文档是什么
> **可检索的方法论错误记忆库**。记录的不是「知识」，而是**做过的错误判断、错在哪一步、以及可复用的判定规则**。
>
> 为什么单独建库：本库已有 [[MEMORY-INDEX]]（架构模式记忆）与 31 处散落的「教训」小节，但**没有一处专门记录「我判断错过的结论」**。错误散落在正文里 = 不可检索 = 必然重犯。
>
> 分层定位：按 [[agent-memory-context-knowledge-design]] 的三级模型，本库属 **L3 长期记忆**。**只把触发规则放进提示词，正文留在本文件**——该文档明确警告「把长期知识硬编码进系统提示词是最高频反模式」。

> [!danger] 录入门槛（不记琐碎错误）
> 只有满足以下**至少一项**才录入：
> 1. 错误**已输出给用户或写入交付物**，可能被当真
> 2. 错误属于**可复现的推理模式**，换个场景还会再犯
> 3. 错误**推翻了一个原本正确或原本错误的结论**，导致结论反复
>
> 拼写、笔误、一次性疏漏不录。

## 速查索引（按「什么时候要回忆」检索）

| 当你准备… | 警戒 | 条目 |
|---|---|---|
| 判定某版本「是否受某漏洞影响」 | 只读了「受影响范围」，**必须同时读「修复版本」** | [[#C-001 只读漏洞公告的一半]] |
| 把「开放端口 / 可达 / 存有凭据」写成风险 | **可达 ≠ 可被利用**；先确认认证方式与凭据强度 | [[#C-002 把可达性外推为可被利用]] |
| 用脚本或工具扫一遍就下「干净」结论 | **扫描器可能是瞎的**；先验证扫描本身有效 | [[#C-003 信任未经校准的扫描结果]] |
| 引用他人（含子代理）的结论 | 对照原始来源复核，尤其**结论数字与计数** | [[#C-004 转述未回溯原始来源]] |
| 改动「别人要读的文件」（日志/配置/产物） | **自检通过 ≠ 读取端会接受**；判据要用对方自己的校验 | [[#C-005 拿工具自检当读取端验收]] |
| 为命令输出设计多行排版 | **渲染端先压平再截断**（控制字节→空格、200 显示格），多行必成一行 | [[#C-006 假设渲染行为而不读渲染端]] |
| 用 `--dump-config` 证明插件能加载 | **它只做配置组合，从不 import 模块**；不存在的包名也照样退出 0 | [[#C-007 拿配置组合当运行时证明]] |
| 用「测试全绿」当「工具可用」的依据 | **夹具形状决定断言的意义**；夹具不是真实产物形状时，全绿也是盲区 | [[#C-008 拿绿色测试当可用性证据]] |
| 看到服务存在就断定效果会出现 | **服务可用 ≠ 效果可达**；准入守卫与挂载点优先级都能让效果消失 | [[#C-009 把服务存在外推为效果出现]] |
| 用条件字段让配置行自动二选一 | **它可能是实时 getter**；判据随挂载进度翻转，可把整个 boot 拖挂 | [[#C-010 把配置字段当作稳定值]] |
| 把参数设成 0 表示「不要这个字段」 | **先测边界值**；截断函数在预算 0 时会留下一个 `…` 占位符 | [[#C-011 只测常规值不测边界]] |
| 本机跑绿就准备推送 / 发布 | **平台专有假设在写它的平台上隐形**；判据是「在目标平台上跑过」，不是「本机跑过」 | [[#C-012 拿本机绿测当跨平台验收]] |
| **写「关于脱敏/安全的说明」文档** | **不要把被脱敏的值当例证写进去**——文档自身也会公开 | [[#C-013 为讲清教训而把敏感字面量写进会公开的文档]] |
| 设计或维护检查工具（扫描/门禁/lint） | **误报会淹没真问题**；豁免必须显式、可审计、最小化 | [[#C-014 检查工具只加模式不加豁免，被误报淹没]] |

> [!tip] 一句话总纲
> 本库 **14 条**错误（截至 2026-09-12）同属一个根源：**把「观察到的现象」直接当成「结论」**。
> 现象 → 需要一步判定 → 才能成为结论。**漏掉中间那一步，就是这十四条。**
> 三个变体：
> · **C-001~C-004** 把**外部信息**当成结论（公告读一半 / 可达当可利用 / 扫描器当眼睛 / 转述当原文）；
> · **C-005~C-012** 把**自己这一侧的通过**当成**对方的验收**（自检当读取端 / 配置组合当加载 / 绿测当可用 / 服务当效果 / 设 0 当删除 / 本机绿测当跨平台验收）；
> · **C-013~C-014** 把**「说明」与「材料」当成两个世界**——写文档时引用被脱敏的值（C-013）、设计门禁时只顾检出不顾豁免（C-014）。两条都在讲：**约束必须覆盖「我自己产出的东西」**。

## C-001 只读漏洞公告的一半

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 核对 `path-to-regexp` 8.4.2 是否受 CVE-2026-4926 影响 |
| 我的错误结论 | 「该版本受影响，且**无补丁可用**」→ 据此判定子代理「漏报一条高危」 |
| 事实 | 公告同页写着 `Patched version: >= 8.4.0`；8.4.2 **已修复**。Debian 与 Ubuntu 追踪库均确认 `Fixed in version 8.4.0` |
| 错在哪一步 | 读了 `Affected versions: >= 8.0.0` 就停止阅读，**没读紧随其后的下一行** |
| 可复用规则 | **判定受影响 = `已装版本 ∈ 受影响范围` 且 `已装版本 < 修复版本`。两个值缺一不可。** |
| 检测方法 | 写完任何漏洞判定，自查：「我引用的修复版本号是多少？从哪一行读到的？」答不出即无效 |
| 波及 | 向用户输出过两次相反结论；已更正并保留记录 |

> [!bug] 加重情节
> 我不仅自己判错，还**推翻了子代理原本正确的结论**。复核他人结论时，若自己的复核依据不完整，会把「对的改成错的」。

## C-002 把可达性外推为可被利用

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 检视本机 MobaXterm 会话记录，发现 4 个公网 IP 的 `root` SSH 会话 |
| 我的错误结论 | 报为**严重项「S8」**：3 台公网主机 22 端口可达 + root 直登 + 凭据存于无主密码的 MobaXterm |
| 事实 | 用户确认**密钥认证、无口令复用**；复检 `MobaXterm.ini` **无任何口令字段**，其私钥目录**无私钥文件**。原判断不成立，已撤回 |
| 错在哪一步 | 三步缺失：① 只测了 TCP 可达，**没验证认证方式**；② 把「21 条会话」误读为「21 条口令」（实际是会话元数据）；③ **没先问所有者**就列入严重项 |
| 可复用规则 | **判定暴露面必须落到三个具体问题：认证方式是什么？凭据强度如何？是否复用？** 三者缺一，就只是「观察」而非「判断」 |
| 补充 | 「公网开放 22 + 使用 root」是**常规配置**，不是缺陷。`root` 是标准用户名，不泄露信息 |
| 元教训 | 过度定级会**稀释真正严重项的可信度**——把常规配置报成严重，读者会开始怀疑整份报告 |

> [!quote] 用户的纠正是对的
> 「root 登录应该本身不构成威胁吧，除非别人入侵了我的电脑」——这个推理链成立。**root 直登 vs 普通用户 + sudo 的风险差异很小**（拿到任一账户后 `sudo bash` 一行即达），业界主张禁用主要为**可审计性**，非漏洞。

## C-003 信任未经校准的扫描结果

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 审计 `~/.dsh/profiles/node_modules` |
| 风险 | 该路径是 **256 个 junction 的农场**，`Get-ChildItem -Recurse` 与 `rg`/`grep` **都不跟随 junction** |
| 实测 | `-Recurse -File` 返回 **0 个文件**（而目录有 628 个） |
| 后果（若未发现） | 任何密钥扫描/依赖审计都会返回「0 命中」，并**被误读为「干净」** |
| 可复用规则 | **下「未发现」结论前，先证明扫描器看得见目标。** 用一个已知存在的样本做阳性对照 |
| 检测方法 | 扫描后问：「我期望至少命中几条？没有命中是好事还是扫描器瞎了？」 |
| 延伸 | 同理适用于：`.gitignore` 排除、权限不足导致的静默跳过、大小写/编码差异 |

## C-004 转述未回溯原始来源

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 采纳子代理的依赖 CVE 审计结论 |
| 现象 | 子代理把 `ws` 的 **CVE-2026-48779 与 GHSA-96hv-2xvq-fx4p 列为两条不同公告**，实际**是同一个**（GHSA 是 GitHub 侧编号，CVE 是通用编号） |
| 另一现象 | 子代理只查了它自己列出的 CVE 编号，**没有反向核对上游项目的官方安全公告**（Express blog 同批就披露了 3 条 CVE） |
| 可复用规则 | 采纳转述结论时：① **核对计数**（「2 条」是不是真的是 2 条不同的事）；② **回溯到项目官方来源**，不只依赖聚合站编号列表 |
| 边界 | 这不意味着不要用子代理——而是**转述必须留下可回溯的原始链接** |

> [!note] 与源码的关系
> 本条不是「子代理不可信」，而是「**转述衰减**」：每经一手，计数与范围都可能漂移。同一份报告里，我也犯了 C-001（自己判错）。

## C-005 拿工具自检当读取端验收

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 设计 `dsh-plugin-redact` 的删行能力：删会话日志（`session.vN.jsonl.zstd`）中间行是否安全 |
| 我的错误结论 | 「删行是安全的通用能力——工具自己的自检（JSON 可解析、头部合法、`seq` 密集）通过，日志就是好的」→ 据此把 `dropLines` 当常规手段写进文档与流程 |
| 事实 | 读取端逐行断言 `event.seq === eventCount`（`seq` 必须等于 0-based 行号）。**删掉中间任意一行 = 整份日志被判损坏 = 会话根本打不开**，不是「少一行」（真实后端实测 `SessionPersistenceCorruptionError`）。安全面只有两个：原地改写（行数/`seq` 全不变）与**后缀**删除（引用一律向后指）；删中间行必须显式 `renumber` 重编号并重映射引用 |
| 错在哪一步 | 从「我这边的自检通过」**直接推广成「读取端会接受」**；中间缺的那一步是**去读读取端的校验代码**——自检清单只覆盖了本工具自己关心的性质 |
| 可复用规则 | **「我检查通过」与「对方会接受」是两件事。** 凡是改动「别人要读的文件」，判据必须是**对方自己的校验**，不是自己的检查清单 |
| 检测方法 | 落结论前问：「这条不变量写在读取端的哪个文件哪一行？」答不出 `文件:行号`，就说明还没验证过 |

## C-006 假设渲染行为而不读渲染端

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 设计 `/redact` 各子命令在 TUI 里的结果排版（清单、备份路径、统计想分行显示） |
| 我的错误结论 | 「输出字符串里写 `\n`，用户在屏幕上就会看到多行」 |
| 事实 | dsh-tui **不直接显示**命令返回的 `text`：先过 `cleanRenderText(text, 200)`（`Chat.js:120` 常量、`:1082` 调用点，实现在 `dsh-adapter/sanitize.js`）——先把 `[\x00-\x1f\x7f-\x9f]`（含 `\n`、`\t`）全部替换成空格、再把连续空白压成一个空格，然后按 **200 显示格**截断并补 `…`（CJK 算 2 格）。**多行必被压成一行，超出必被砍尾**，绕不过去 |
| 错在哪一步 | 按「输出该长什么样」的直觉做设计，**没有去读渲染端**。发现时两轮排版工作已作废，所有输出推倒重来：单行 + ` · ` 分隔 + 最重要信息在最前 |
| 可复用规则 | **输出格式是消费端的属性，不是生产端的自由度。** 面向 UI 的输出，先读它的压平/截断代码，再决定排版 |
| 检测方法 | 找到消费这段文本的那个函数，读它的替换正则与截断常量；说不出函数名与常量值，就说明还没读过 |

## C-007 拿配置组合当运行时证明

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 用 `dsh --profile <name> --dump-config` 确认插件挂载（写进 README §2.4 与安装检查清单） |
| 我的错误结论 | 「dump 里出现 `id: dsh-redact` 这一行 ⇒ 插件能加载、命令能注册」 |
| 事实 | `--dump-config` **从不 import 插件模块**，只做配置层的组合（`applyEntryPatches`）。实测：补丁里插入一行 `name: dsh-plugin-totally-nonexistent-xyz`（`boot-verify\bogus-patch.yml`），dump 照样打出该行、进程照样**退出码 0**；只有真 boot 才会在 import 阶段报 `Cannot find package 'dsh-plugin-does-not-exist-xyz'` |
| 错在哪一步 | 把**配置组合阶段的检查当成运行时检查**：把「这行出现在合成结果里」读成「这行会被加载」，跳过了「组合 → import → apply → ACTIVE」这条链路 |
| 可复用规则 | **配置检查只证明配置，不证明加载。** 要证明插件真的起来，判据是启动后的行状态（ACTIVE）与它注册出来的命令，不是 dump 文本 |
| 检测方法 | 用一条**明知会失败**的行（不存在的包名 / import 即抛错的模块）跑同一个检查；它若照样「通过」，这个检查就不能用来证明成功 |

## C-008 拿绿色测试当可用性证据

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 以 `dsh-plugin-redact` 三套自测（`handler.selftest.mjs` 159 / `bugfix-regression.mjs` 48 / `session-surgery\selftest.mjs` 34，共 241 条全绿）作为「工具可用」的依据，并写进交付物 |
| 我的错误结论 | 「三套全绿 ⇒ 工具工作正常、输出能被打开」 |
| 事实 | `bugfix-regression.mjs` 的夹具**不是读取端合法日志**：第 30/142 行把 tool/result 写成 `{ role:'tool', source:{callId:'aa'} }`，真实形状是 `role:'user'` + `source:{kind:'tool',callId}`。用真实 `JsonlSessionPersistence.open()` 一跑就报 `session event at seq 4 message must have role "user"` / `has invalid source`。**绿色断言对「读取端能否打开输出」零信息量**；而红队找到的两条不可逆缺陷（F1 `sourceEventSeqs` 游程未重映射、F2 `session/title.messageSeqs` 悬空）恰好都住在这个盲区里 |
| 错在哪一步 | 把「我的断言全过了」当成「系统正确」，**没问「这套测试会漏掉什么」与「我的夹具和真实产物同形状吗」** |
| 可复用规则 | **测试的可信度上限 = 夹具与真实产物的同形度。** 改动别人的产物时，判据必须是**真实消费者**（真实读取端/后端），并至少留一条「真实消费者能打开输出」的断言 |
| 检测方法 | ① 每条断言问一次「它为假时，是夹具错了还是实现错了？」② 把夹具喂给真实消费者跑一遍：绿着却被消费者拒绝 = 夹具在说谎 |

## C-009 把服务存在外推为效果出现

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | `/redact pick` 面板：以「`ctx.get('tuiDialogs')` 有值 ⇒ 面板会弹」为前提设计交互与配置说明 |
| 我的错误结论 | 「对话框服务存在（且请求被接纳），面板就会出现」 |
| 事实 | 被证伪两次。**(a) 准入守卫**：`tuiDialogs` 运行时在 `try/catch` 之外还有一道准入（`dsh-adapter/dialogs.js:103-111`，`bindOwnerEffect` 失败即 `pending.onAbort()`）。本行若早于 composition-root tracker 建立而进入 ACTIVE，每次 `select` / `confirm` 只写一条 logger warning 就返回取消值——**面板从不渲染，用户只看到「已取消」**（加行级 `inject` 后实测从 0/6 变 6/6）。**(b) 挂载点被压掉**：面板**唯一**的实例化点是 `Chat.js:3585`，而 `approvalPanelNode` 在三元链里排在它前面、无提示压掉它；此时键盘让出（`Chat.js:2566`）已经生效、approval 又没有超时——**服务在、请求挂在 store 里、键盘已交出、面板永不渲染**（根因报告 §2.2 矩阵：7 个死锁态，A1 只要一个 approval 挂起就成立） |
| 错在哪一步 | 验证停在「服务可用」这一层，**没有验证「服务调用 → 效果可见」整条链路**：准入、挂载点优先级、键盘归属是三道各自独立的闸门，任何一道关闭，效果就不存在 |
| 可复用规则 | **服务存在 ≠ 效果可达。** 依赖 UI 效果时，要么把「效果真的出现」当判据，要么换成**结构上不可能失败**的路径（最终改成不把 promise 停进 store 的两段式命令 `nodes` → `hide <序号> --commit`） |
| 检测方法 | 把「服务在」与「效果在」当两次独立观测；只要两者之间存在任何带优先级的挂载/准入分支，就按最坏顺序逐条走一遍 |

## C-010 把配置字段当作稳定值

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 为 `dsh-redact` 行写「有 `tuiDialogs` 提供者就启用、没有就跳过」的 `!!js disabled` 自禁用守卫，想让两种 profile 自动二选一 |
| 我的错误结论 | 「`disabled` 是个布尔字段，写个判据就能自动二选一」 |
| 事实 | `Entry.disabled` 是**实时 getter**，每次读取都重新求值。判据（`![...ctx.loader.entries()].some(e => e.options.name === '…' && !e.disabled)`）依赖挂载进度，同一行会在 boot 过程中从「被跳过」翻成「被算作加载失败的行」；启动器把未激活/PENDING 的行升级为致命错误——**整个 boot 中止**（提供者排在后面时必炸），不是单行静默降级 |
| 错在哪一步 | 把配置字段当**稳定值**读，而它其实是**表达式**；没有问「这个判据在 boot 的哪一刻求值、那一刻输入就绪了吗」 |
| 可复用规则 | **配置里能求值的东西，都要问「什么时候求值、求值几次」。** 判据依赖其它行的挂载状态时，不能用来决定本行是否加载；要二选一就用**静态的两层**（TUI 层与非 TUI 层），不要用运行时判据 |
| 检测方法 | 对任何 `!!js` / 条件字段，指出它的求值时刻与当时的输入状态；做不到就改设计 |

## C-011 只测常规值不测边界

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 给 `argsCells`（命令行显示格预算）留隐私开关，文档声明「`0` = 完全不显示命令行，连 `…` 都不会有」 |
| 我的错误结论 | 「预算设成 `0` 就等于这个字段不存在」 |
| 事实 | 截断函数 `clamp(s, budget)` 在 `budget = 0` 时循环第一步就 `break`，返回 `'' + '…'` —— **一个只剩 `…` 的占位符**。于是这个「隐私开关」反而在清单文件与面板里留下痕迹，只有调用点外层的 `argsCells > 0` 把它盖住。修法是在 `clamp` 里对 `budget <= 0` 短路返回 `''`（注释就在 `index.js:42-44`） |
| 错在哪一步 | 只按**常规值**（默认 120、自定义值）验收，**没有把参数推到边界**（`0` / 负数）；把「文档里写了 `0` 的含义」当成「`0` 的行为已验证」 |
| 可复用规则 | **凡是「设为 0 / 空 / false 即关闭」的开关，必须单独测这个边界值**，判据落在成品上（产物里到底有没有那个字符），而不是「分支有没有走到」 |
| 检测方法 | 对每个「关闭档」参数跑一次并逐字符检查产物；出现 `…`、占位符或空段残留，就是关闭不彻底 |

## C-012 拿本机绿测当跨平台验收

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | `dsh-redaction` 仓库第一次跑 GitHub Actions CI（`ubuntu-latest`）。在此之前，全部开发与自测都在 Windows 上完成，两个包的 9 套套件本地全绿 |
| 我的错误结论 | 「本机 9 套全绿 ⇒ 交付物在任何平台都跑得起来；CI 只是把本机已经做过的事再做一遍」——于是 CI 一直没推上去，也没有人觉得这件事着急 |
| 事实 | CI **37 秒就红**。失败点为 `packages/dsh-plugin-redact/test/preflight.mjs`：`TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received undefined`，位置在 `path.join`——**不是断言失败，是套件根本起不来**。根因是该文件用 **`process.env.USERPROFILE`** 推导 DSH 主目录；这个环境变量**只存在于 Windows**，在 `ubuntu-latest` 上是 `undefined`，于是 `path.join(undefined, '.dsh')` 直接抛错 |
| 为什么是**发布物缺陷**而不是 CI 配置问题 | `test/preflight.mjs` 在 `package.json` 的 `files` 白名单里，**会随包发布** ⇒ **任何 Linux / macOS 消费者跑 `npm test` 都会炸**。CI 只是第一个把它说出来的东西 |
| 同批另两处同类 | ① `new URL(import.meta.url).pathname`（2 个文件）：`.pathname` 是 **URL 组件**不是文件系统路径，目录含空格/中文时残留 `%20` 转义（Windows 上还会多出 `/C:/…` 前导斜杠），正确写法是 `fileURLToPath(import.meta.url)`；② 同一份 `engine.selftest.mjs` 在仓库与实际部署处**各有一份拷贝**，部署那份有一段夹具清理代码而仓库那份没有 → 每跑一次测试就在源码目录留下 `broken.zstd`、`needle.txt`、`plan-*.json`（同一文件两份拷贝悄悄分叉） |
| 错在哪一步 | 把「**在我这台机器上通过**」当成「在别人的机器上会通过」。**平台专有假设在写它的平台上隐形**——本地永远绿，因为本地从来就是它假设的那个平台。缺的那一步是**在目标平台上真的跑一次** |
| 可复用规则 | **平台假设必须由目标平台来验收。** 判据是「在目标平台上跑过」，不是「本机跑过」。跨平台交付物在推送/发布前，至少要在**一个目标平台**上执行一遍与 CI 相同的步骤 |
| 检测方法 | ① 搜平台专有符号：`USERPROFILE` / `HOMEDRIVE` / `APPDATA` / `LOCALAPPDATA`、`import.meta.url` 配 `.pathname`、字符串字面量里的盘符、`path.win32`；② 对每条命中问「它在目标平台上是什么值」——后面没有紧跟 `??` 或 `||` 回退的就是缺陷；③ 把这份检查固化成**静态守卫 + 自检**（见下） |
| 波及 | CI 首跑即暴露；修复后推送前在本地 1:1 复现 `ubuntu-latest` 全流程 **7/7 步全绿**，Windows 侧 9/9 套件全绿。缺陷**未流向任何消费者** |

> [!bug] 修法很浅，防线才是这条记录的价值
> 修复动作本身都不难：`os.homedir()` 取代平台专有环境变量、`fileURLToPath` 取代 `.pathname`、把夹具清理块补回仓库副本、`.gitignore` 兜底。真正让这条不再重犯的是新增的 **`.github/scripts/portability.mjs` 静态守卫**——扫两个包的**发布代码与测试**，四条规则：
> 1. 平台专有环境变量（`USERPROFILE` / `HOMEDRIVE` / `APPDATA` / `LOCALAPPDATA`）后面没有紧跟 `??` 或 `||` 回退；
> 2. `import.meta.url` 与 `.pathname` 出现在同一处；
> 3. 字符串字面量里硬编码盘符；
> 4. `path.win32`。

> [!warning] 守卫自己的两个假判据（比缺陷本身更值得记）
> 1. **行级判断 ≠ 变量级判断。** 第一版把「**这一行里**出现过 `??`」当作安全信号，于是 `DSH_HOME ?? path.join(process.env.USERPROFILE, '.dsh')` 被判为**安全**——而这**正是要抓的那个 bug**。正确判据是：回退必须属于**那个变量本身**（紧跟其后），而不是属于这一行。
> 2. **±2 行窗口会被自己的注释命中。** `import-meta-pathname` 规则最初用 ±2 行窗口匹配，结果被它**自己那句解释性注释**（注释里写了 `.pathname` 四个字）误报。改成只在**同一行、同一表达式内**匹配。
>
> 两条合起来是一条规则：**守卫的判据必须与缺陷同形**（变量级，而不是行级），**匹配范围必须窄到不会命中解释性文字**。

> [!important] 守卫必须可证伪
> 配套的 `portability.selftest.mjs` 会**把真实的 `USERPROFILE` 缺陷重新注入 `preflight.mjs`**，断言守卫必须（a）以**退出码 1** 失败、（b）**指名正确的文件与正确的行号**，然后用 `finally` 把原文件恢复。理由：**不会失败的检查比没有检查更糟**——它把「没查」伪装成「查过了」。
> 顺带一个细节：自检最初把期望行号写死成 `13`，后来在文件顶部加了一行 import 就红了；改成从注入后的内容里**动态推算**行号——判据不能依赖「文件此刻长什么样」。

## C-014 检查工具只加模式不加豁免，被误报淹没

| 项 | 内容 |
|---|---|
| 发生 | 2026-09-12 |
| 场景 | 按 C-013 的结论实现 `scripts/prepush-selfscan.sh` 后**首次运行** |
| 现象 | 脚本在 `README.md` 报 2 处、在合并记录报 1 处「命中」，**全部是文档示例**（截断密钥的占位写法、`-p` 加省略号的示意、讨论用户名路径的说明文字） |
| 若不理会的后果 | 每次扫描都有固定误报 → 使用者习惯性忽略输出 → **真凭据混在误报里被放过**。检查工具沦为形式 |
| 错在哪一步 | 只设计了「发现即阻断」，**没设计「如何表达合法的例外」** |
| 可复用规则 | **任何检查工具必须同时给出两样东西：检出模式 + 显式豁免机制。** 豁免要**可见、可审计、最小化**——不允许靠模糊正则去「猜」哪些是示例，否则真凭据也会被猜成示例而漏掉 |
| 我的处置 | ① 收窄模式：`-p` 后的中文省略号不再匹配（只接受字母数字类实参）；本机用户名只在**路径形态**下报警；② 引入 `scan-ignore` 行内注释作为显式豁免；③ 加 `--self-test` 自证脚本自身不含凭据 |
| 检测方法 | 工具上线前自问：「如果我是使用者，第一次跑就见到误报，我还会认真看第二次吗？」 |
| 元教训 | **门禁的价值等于其信噪比，而非覆盖度。** 覆盖再全，只要误报率高就会被绕过——这与 C-002「过度定级稀释可信度」是同一道理 |

> [!note] 与 C-003 / C-012 的对称性
> C-003 是「扫描器太瞎」（漏报），C-014 是「扫描器太吵」（误报）——**两者都会让检查失效，而失效方向相反**。
> C-012 的守卫也曾被**自己的解释性注释**误报（改用同一行同表达式匹配）。三次是同一类问题的不同面：
> **检查的判据必须与缺陷同形，匹配范围必须窄到不会命中说明性文字；同时必须留出显式豁免。**

## 录入协议

新增条目时：

1. **编号**：`C-00N`，递增，**不复用已撤回条目的编号**
2. **必填六项**：发生时间 / 场景 / 我的错误结论 / 事实 / 错在哪一步 / 可复用规则
3. **必须写「检测方法」**——没有可执行的检出手段，这条记忆就无法在下次生效
4. **同步更新速查索引**（表格首行），否则等于没录
5. **不改写已录条目**——若某条后来被推翻，新增一条并回链，而不是修改原文（保留「我错过」这个事实本身）
6. **撤回的结论也要录**（如 [[#C-002 把可达性外推为可被利用]]）——**撤回比错误本身更有价值**，因为它标出了哪类推理会产出假阳性

> [!warning] 本库自身的失败模式
> 错误记忆库最危险的失败不是记错，而是**记了却没人查**。
> 因此：任何结论在被写入交付物前，应回查本库速查索引一次；发现命中即按对应规则重检。
> 该触发规则已写入 [[AGENTS]]，使新会话的 Agent 能载入本库。
