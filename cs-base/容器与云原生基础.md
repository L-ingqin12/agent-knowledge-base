## 一、容器不是虚拟机：三件套推演

| 机制 | 管什么 | 一句话原理 |
|------|--------|-----------|
| namespace | **看得见什么**(视图隔离) | pid/mnt/net/uts/ipc/user 各自成轴，clone(flag) 时创建；另有 **cgroup**(`CLONE_NEWCGROUP`, 4.6) 与 **time**(`CLONE_NEWTIME`, 5.6；`time_for_children` 5.6、`max_time_namespaces` 5.7) |
| cgroup | **能用多少**(资源配额) | cpu/memory/io/pid 挂树限流；**v2 统一层级**（no internal process 约束：带控制器的 cgroup 不能同时放进程与子 cgroup，threaded subtree 例外）；OOM kill 按 memory 层打分，`memory.oom.group` 可把整组当"不可分割负载"一起杀，且 cgroup 内触发 OOM killer **不会杀到该 cgroup 之外**；压力观测走 PSI（每层 `cpu.pressure`/`memory.pressure`/`io.pressure`） |
| unionfs(overlay2) | **文件从哪来** | lowerdir(镜像只读层) + upperdir(容器可写层) 联合挂载，**文件级 copy-up**：首次修改才把整个 lower 文件连同其父目录复制到 upper 层——大文件首写因此变慢；不显式 fsync 时崩溃可能留下全零上层文件，故 overlayfs 在 rename/link 完成 copy up 前会 fsync 上层文件；metacopy 模式可只先拷元数据（chown/chmod 场景），数据等 WRITE 打开再拷 |

- namespace 两个补充轴的含义：**cgroup namespace** 让容器内 `/proc/self/cgroup` 只看到 `/`；**time namespace** 让容器独立调整 `CLOCK_MONOTONIC`/`CLOCK_BOOTTIME` 偏移（容器内改时钟偏移不再需要特权 hack）
  > 来源：https://man7.org/linux/man-pages/man7/namespaces.7.html

- `docker run` 的内核事实 = 一个带全套 namespace 标志的 clone() + cgroup 归组 + pivot_root 切根 —— **没有 guest kernel**（对比 VM 的 hypervisor+独立内核），所以启动 ms 级、密度千级/机
- 进入容器即 `nsenter` 进目标 namespace 集——"ssh 进虚拟机"的心智是错的

> cgroup v2 与 PSI 出处：https://docs.kernel.org/admin-guide/cgroup-v2.html · https://docs.kernel.org/accounting/psi.html
> overlayfs copy-up 出处：https://docs.kernel.org/filesystems/overlayfs.html

## 二、镜像分层工程学

```dockerfile
# 分层缓存: 变化少的在前, 依赖安装单独成层(代码改动不触发重装)
FROM golang:1.22 AS build       # ← 每个阶段都必须以 FROM 开头(多阶段构建的语法要求; 原片段缺这一行)
COPY go.mod go.sum ./
RUN go mod download          # ← 依赖层(稳定)
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o app .   # ← 静态编译见下
FROM gcr.io/distroless/static AS final   # 多阶段: 构建环境不进最终镜像
COPY --from=build /app /app              # 只搬产物; distroless 无 shell, 排障需换 debug 变体 tag
```

> [!warning] 更正（2026-09-13）：原片段从 `COPY go.mod` 开始、只在末尾出现 `FROM`，缺少构建阶段（多阶段构建的每个阶段都以 `FROM … AS <stage>` 开头，`RUN go mod download` 因此没有来源镜像）——作为完整 Dockerfile 不成立，已补 `FROM golang:1.22 AS build` 与 `COPY --from=build`。验收判据：`docker build` 通过、`docker history` 复核层数与体积、distroless 无 shell 时用 debug 变体 tag 排障。（原表述为「片段从 COPY go.mod 开始、只在末尾出现 FROM gcr.io/distroless/static」）
> 来源：https://docs.docker.com/build/building/multi-stage/

- 层内容寻址(SHA256)→相同层跨镜像共享存储与传输；`docker history` 逐层审计体积
- **多阶段构建 + distroless/scratch** 是安全与体积双优解；glibc 动态二进制换 alpine(musl) 有 DNS 兼容税（[[LibC与动态链接]] §一 nsswitch 差异）
- `.dockerignore` 防 secrets/构建产物入层——**层即使后删也留在历史里**，密码写进早期层再 RM 无效

## 三、K8s：声明式 API 与控制循环

```
期望状态(yaml) ──提交──▶ etcd ──watch──▶ 控制器(Reconcile 循环: 观测diff→行动收敛)
调度器: 过滤(资源/亲和性/taint容忍) → 打分(均衡度/镜像局部性) → 绑定节点
kubelet: CRI 拉镜像建容器 → 探针(liveness 重启 / readiness 摘流量 / startup 缓启动)
```

- 心智转变：命令式("帮我起个容器") → 声明式("集群应长这样"，控制器永续收敛)——自愈/滚动更新/水平扩缩全是同一循环的不同表现
- Service/Ingress 流量路径：ClusterIP(iptables/IPVS 规则随机选后端) → Ingress(L7 路由)；DNS 名 `<svc>.<ns>.svc.cluster.local`
- 配置注入两通道：ConfigMap(env/volume)+Secret(base64 非加密!需 RBAC+etcd 加密配合)

## 四、资源管理与排障速查

| 症状 | 根因域 | 动作 |
|------|--------|------|
| Pod 反复重启 | liveness 误杀/应用 OOM | `describe` 看 exit code: 137=cgroup OOMKill → 提 limit 或查泄漏([[LibC运行时排查-TLS与锁]] §四) |
| CPU throttling 毛刺 | limit 限流周期内耗尽 | 降低 limit 或放宽; P99 尾延迟元凶之一 |
| CrashLoopBackOff | 启动即退 | logs --previous; readiness/liveness 起始延迟不足 |
| ImagePullBackOff | 凭证/网络 | imagePullSecrets; 私仓连通 |
| 服务不通 | 网络/标签选择器 | endpoints 是否有 IP → NetworkPolicy → kube-proxy 模式 |

资源模型：requests(调度依据) vs limits(运行上限)——**Guaranteed(requests==limits)** 给延迟敏感负载；超卖比是容量规划核心参数。

## 六、待确认项

> ① cgroup v2 全量默认化的发行版覆盖；② eBPF 替代 kube-proxy(Cilium 路线)的生产占比；③ sidecar-less(原生 sidecar 容器/Istio ambient)演进对服务网格成本的影响。

> [!warning] 残余复核（2026-09-13）：三条**均仍开放**——它们是「覆盖率 / 占比 / 成本影响」类统计与基准，要发行版发布说明、社区调研、厂商 benchmark 三类外部输入；本机是 Windows 宿主、无任何 Linux 发行版可查（`docker` CLI 在但 daemon 未运行，`docker info` 连不上），离线不可定。
> - ① 判据：逐发行版抓发布说明或内核默认命令行，确认是否默认 `systemd.unified_cgroup_hierarchy=1`（候选：Fedora 31+、Ubuntu 21.10+、Debian 11+、RHEL 9+，并补上仍以 v1 为默认的 LTS 行）；另一头要核对**容器运行时/K8s 版本**对 v1 的支持状态，否则「全量默认化」只说了半边。
> - ② 判据：抓 CNCF 年度调研（CNCF Annual Survey）中 kube-proxy replacement / eBPF 数据面的采用率条目，再用 Cilium 官方公布的采用数据交叉印证；单一来源不算占比。
> - ③ 判据：抓 Istio ambient 官方博客与发布说明里的基准（sidecar vs ambient 的每 Pod / 每节点 CPU、内存、延迟），把「成本影响」落到资源数字；定性描述（「更省」）不构成答案。

> [!success] 残余复核（2026-09-13 联网轮）：**① 与 ③ 已结**（① 把「全量默认化」改写为**按发行版逐条的默认线**；③ 取到官方**每代理**资源数字）；**② 仍开放——但已证伪其数据源**（CNCF 年度调研里根本没有这个条目）。
> - **① 已结（改写口径）**：原表述「cgroup v2 全量默认化」不成立，正确写法是**逐发行版给出默认线**，本轮核到四条（均为官方来源）：
>   - **Fedora 31**：官方 Fedora wiki 变更页标题即 **"Modify Fedora 31 to use CgroupsV2 by default"**，`Targeted release: Fedora 31`。
>   - **Ubuntu 21.10（impish）**：官方 Ubuntu systemd changelog 中 `systemd (248.3-1ubuntu4) impish` 含 **"Use upstream's default -Ddefault-hierarchy=unified. (LP: #1850667)"**，后一条目并复述「248.3-1ubuntu4 changed to default to a unified cgroups hierarchy」。**注意来源是 changelog，不是 release notes**（Ubuntu 该版 release notes 是空壳，社区亦无对应主题页）。
>   - **Debian 11（bullseye）**：官方 systemd changelog `systemd (247.2-2)` 含 **"Switch to "unified" cgroup hierarchy (i.e. cgroupv2) (Closes: #943981)"**。**注意来源是 changelog**——原判据点名的 `wiki.debian.org/DebianUnifiedCgroupHierarchy` 本轮**不可达**（该 wiki 有 JS 工作量证明拦截，过掉后仍 403；Wayback 对该 URL **无快照**），故改用 changelog 这一官方来源。
>   - **RHEL 9**：Red Hat 官方文档原文 **"In RHEL 9, the new version of control groups, cgroups v2, is enabled by default."**（9.0 release notes 亦有 "cgroup-v2 enabled by default in RHEL 9"）。（取回路径备注：docs.redhat.com 对本机直连返回 403，经文本渲染服务按其原 URL 取得。）
>   - **容器运行时 / K8s 那一半**：官方 Kubernetes 博客 *Kubernetes 1.31: Moving cgroup v1 Support into Maintenance Mode*（2024-08-14）——「the community has decided to move cgroup v1 support into maintenance mode in v1.31」，维护模式 = 冻结新特性、仅保留关键安全修复与尽力而为的缺陷修复。
>   - **仍缺的部分**：**仍以 cgroup v1 为默认的老 LTS（如 RHEL 8 线）本轮未核**，故本条不得写成「已全量默认化」——应写作「主流新版本发行版已默认 v2，老 LTS 需逐条核」。
> - **③ 已结**：Istio 官方性能文档给出**每个代理**的资源数字（口径：Istio 1.24，1000 req/s、每请求 1 KB 载荷）——**单个 sidecar（2 worker 线程）约 0.20 vCPU / 60 MB；单个 waypoint（2 线程）约 0.25 vCPU / 60 MB；单个 ztunnel 约 0.06 vCPU / 12 MB**。官方基准方法为：5 台 M3 Large 裸金属、Flannel 作主 CNI、`http/1.1`、1 KB 载荷、500/750/1000/1250/1500 req/s、4 条客户端连接、2 个 proxy worker、启用双向 TLS。**关键限定（必须照写）**：这些数字是**按代理**计的（sidecar/waypoint 每 Pod 一个、ztunnel 每节点一个），**官方并未给出合并后的「每节点 vCPU 总量」**；GA 博客只有定性外加上限表述「In some use cases, the savings can exceed 90% or more」。
>   - 版本与演进：**ambient 在 Istio 1.24 达到 GA**（2024-11-07 公告；1.24 release notes：「The core features (ztunnel, waypoints and APIs) have been marked as Stable by the Istio TOC.」，1.22 为 beta）；另有 2025-03-06 的官方性能博文改用 `iperf` 测带宽（版本 1.26 预发布、默认设置），并称 **"Over the last 4 releases, the performance of Ztunnel has improved by 75%"**。
>   - 与「**原生 sidecar 容器**」这条路线的关系（同一成本问题的另一半，本轮一并核了官方状态）：Kubernetes 官方文档 *Sidecar Containers* 标注 **Feature state: Stable since Kubernetes v1.33**（"It was first available in the v1.28 release."），且**已锁定不可关闭**（"You can no longer disable or opt out of this feature or behavior (it is locked)"）。即：**原生 sidecar 是把「每 Pod 一个辅助容器」这一形态正式固化**，与 ambient 的「每节点 ztunnel + 可选 waypoint」是**两条方向相反的成本路线**——前者降低编排复杂度、**不**消除每 Pod 开销；后者消除每 Pod sidecar，代价是 L7 需额外 waypoint。
> - **② 仍开放（已证伪数据源，判据收窄）**：**CNCF 年度调研中没有「kube-proxy replacement / eBPF 数据面」这一条目**——对官方 2021 / 2024 / 2025 三份年度调研报告 PDF 做全文检索，`kube-proxy`、`kubeProxyReplacement`、`eBPF` **均零命中**（2022/2023 只有信息图、无文本 PDF）。因此「eBPF 替代 kube-proxy 的生产占比」**在 CNCF 口径下不存在**，原先「抓 CNCF 年度调研」的判据**不成立**，判据改写为：若仍要该数字，须另找**独立**来源，且必须区分它回答的是**项目采用率**还是**数据面替代率**。可用的相邻 CNCF 数字只有**项目采用率**（2024 年度调研 Figure 13，Cilium「Using in Production」= **18%**，Q32，样本 689），**不得**把这个数字当作「eBPF 替代 kube-proxy 的生产占比」，也**不得**用 Cilium/Isovalent 厂商数字顶替。
> 依据：https://fedoraproject.org/wiki/Changes/CGroupsV2 ；https://changelogs.ubuntu.com/changelogs/pool/main/s/systemd/systemd_249.11-0ubuntu3/changelog ；https://metadata.ftp-master.debian.org/changelogs/main/s/systemd/systemd_247.3-7+deb11u5_changelog ；https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html-single/considerations_in_adopting_rhel_9/index ；https://kubernetes.io/blog/2024/08/14/kubernetes-1-31-moving-cgroup-v1-support-maintenance-mode/ ；https://istio.io/latest/docs/ops/deployment/performance-and-scalability/ ；https://istio.io/latest/blog/2024/ambient-reaches-ga/ ；https://istio.io/latest/blog/2025/ambient-performance/ ；https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/ ；https://www.cncf.io/wp-content/uploads/2025/04/cncf_annual_survey24_031225a.pdf （取回于 2026-09-13）
