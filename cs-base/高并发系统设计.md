# 高并发系统设计

> [!abstract] 定位
> 从 C10K 到分布式的高并发方法论：连接模型、线程池与无锁、缓存三级、削峰队列、限流熔断降级、数据层拆分。每节挂库内实践锚点——本库 Sidecar 会话池背压、LogNet 批量写入即这些模式的实例。

See also: [[CS-KB-Home]] · [[操作系统八股]] · [[计算机网络八股]] · [[opencode-pi-base-development-analysis]]

## 一、演进主线：C10K → C10M

| 阶段 | 模式 | 天花板 |
|------|------|--------|
| C10K | 一连接一线程 | 线程栈+切换成本 |
| 事件驱动 | epoll/kqueue + Reactor | 单机数十万连接 |
| 内核旁路 | io_uring / DPDK / SO_REUSEPORT 多进程分片 | 百万级（内核协议栈成为瓶颈时） |

对应 OS 层机制见 [[操作系统八股]] §五 IO 路径。

## 二、计算侧：线程池与锁优化

- **线程池参数**：CPU 密集 ≈ 核数；IO 密集 ≈ 核数×(1+等待比)；队列有界防 OOM，拒绝策略要显式
- **锁粒度**：分段(ConcurrentHashMap 思想) → 读写锁 → CopyOnWrite(读多写极少) → 无锁 CAS(注意 ABA：加版本号)
- **伪共享**：跨核变量同 cache line 互相打脸 → alignas(64) 填充
- 库内锚点：[[log-analysis-agent-windows-architecture]] 的 ThreadPoolExecutor 异步隔离；[[agent-async-isolation-pattern]] 的三层超时包装

## 三、数据侧：缓存三级与一致性

```
本地缓存(LRU/LFU) → 分布式缓存(Redis) → DB
```

- 三连问：**穿透**（查不存在）→ 空值缓存/布隆过滤器；**击穿**（热 key 过期瞬间）→ 互斥重建/逻辑过期；**雪崩**（批量同时失效）→ 过期时间抖动
  - 布隆过滤器三条硬性质：**只增不删**（标准实现无删除）/ **有误判无漏判**（判"不在"必准，判"在"可能假阳）/ 位数组长度与哈希个数按"预期元素数 + 目标误判率"算
  - 与空值缓存的取舍：空值缓存实现最简但 key 会膨胀、需短 TTL；布隆过滤器省内存但要预热与容量预估；**需要删除**时换 counting bloom / cuckoo filter
  - 落地形态：Redis 8.0 起概率结构可内置——Bloom filter、cuckoo filter、count-min sketch、top-k、t-digest（部分原为独立模块），不必再单独引模块
  > 来源（仅背书"Redis 8.0 内置概率结构"一条）：https://redis.io/blog/redis-8-ga.md
- 一致性谱系：先更 DB 再删缓存(Cache Aside 默认) → 订阅 binlog 异步删 → 强一致需分布式锁（代价自评）
- 热 key：本地副本打散 / key 加随机后缀分片

## 四、流量侧：削峰与过载保护

| 手段 | 场景 | 要点 |
|------|------|------|
| 消息队列 | 写削峰/异步解耦 | 至少一次投递→消费端**幂等**（去重表/状态机） |
| 限流 | 保护自身 | 计数器→滑动窗口→令牌桶(匀速发牌)→漏桶(整形)；nginx `limit_req` 即漏桶实现，对账表见下 |
| 熔断 | 防雪崩蔓延 | 错误率/慢调用比例触发半开试探 |
| 降级 | 保核心弃边缘 | 预设开关+预案演练 |
| 背压 | 上游感知下游水位 | TCP rwnd/队列深度反馈 |

限流算法对账（算法 × 关键参数 × 超限表现 × 观测指标，以 nginx `limit_req` 的漏桶实现为锚点）：

| 算法 | 关键参数 | 超限表现 | 观测指标 |
|------|---------|---------|---------|
| 计数器 | 窗口长度、阈值 | 窗口边界处可放行 2 倍流量 | 拒绝计数 |
| 滑动窗口 | 子窗口粒度 | 平滑，用内存换精度 | 拒绝计数 |
| 令牌桶 | rate、burst | 桶空即拒，burst 决定突发额度 | 桶余量 |
| 漏桶（nginx `limit_req`） | rate、burst、`nodelay`、zone 大小 | 排队延迟或直接拒绝；zone 存满时按 LRU 淘汰旧状态，连新状态都建不了则**终止该请求** | `$limit_req_status`：PASSED / DELAYED / REJECTED / DELAYED_DRY_RUN / REJECTED_DRY_RUN（1.17.6+；`limit_req_dry_run` 自 1.17.1） |

- 容量换算：1MB zone ≈ 16k 个 64 字节状态 或 8k 个 128 字节状态——zone 是隐藏容量参数，漏配就是隐性限流失效
> 来源：https://nginx.org/en/docs/http/ngx_http_limit_req_module.html

> [!tip] 本库映射
> Agent 会话池的 cache 亲和+排队背压（[[opencode-pi-base-development-analysis]] §会话池）；质量门控 RETRY 预算=对 LLM 上游的限流降级组合（[[state-machine-quality-gate-loop]]）。

## 五、存储侧：读写扩展

- **读写分离**：主从复制延迟→读己之写走主/会话粘滞
- **分库分表**：垂直按业务、水平按键；分片键选查询最高频维度
- **一致性哈希**：环+虚拟节点，扩缩容只动邻段数据（缓存节点增减/分片路由通用）
- **分布式 ID**：号段/雪花(时钟回拨问题)/UUID v7 时间有序（标准出处 RFC 9562，2024-05 发布、**作废 RFC 4122**：v7 = `unix_ts_ms` 48 位 + 版本位 4 位(0b0111) + 其余 74 位随机；同标准另有 v6 重排 v1、v8 自定义）
- 事务边界：能单分片不跨分片；跨分片 saga/TCC/最终一致（强一致两阶段提交吞吐差）

> 标准出处：RFC 9562（Standards Track, May 2024, Obsoletes 4122）——https://www.rfc-editor.org/rfc/rfc9562.html

## 六、容量估算模板（面试万能框架）

```
QPS = 日请求量 / 有效秒数(常取峰值系数)
带宽 = QPS × 平均响应体
内存 = 并发 × 会话状态
再按 读多写少→缓存优先 / 写多→异步+分片 决策
```

LLM 服务特化：并发受 KV 显存约束而非 CPU——token 吞吐×上下文长度才是"QPS"（对照 [[LLM推理部署与量化]]）。

## 六·补、端到端实战推演：设计一个 10k QPS 短链服务

把前六章的零件装成一栋房子——每一步都给出**数字是怎么算出来的**。

### 第 1 步：需求量化（§六模板落地）
```
读:写 = 100:1 (短链服务的典型形态)
写入 100 QPS → 读 10,000 QPS; 峰值系数 3x → 设计目标 写300/读30k
存储: 100QPS×年 ≈ 31.5 亿条 × ~100B/条 → 约 315GB/年, 缓慢增长
带宽: 30k QPS × 平均响应 200B(302+短body) ≈ 6MB/s 出口, 微不足道
结论: 这是个【读爆炸+写温和+存储缓慢增长】系统 → 缓存层是主战场
```

### 第 2 步：读路径设计（缓存三级套用 §三）
```
请求 → [本地 LRU, TTL 60s] → [Redis: hash code→url] → [MySQL]
- 本地放第一级的理由: 访问呈 zipf 长尾, top 1% 链接覆盖 ~90% 流量,
  本地命中直接省网络 RTT(~0.5ms)与 Redis 带宽
- Redis 容量核算: 全量放不下也不必——只缓存近 7 天创建或被访问过的键:
  约 2 亿键 × (key8B+val60B+overhead80B) ≈ 30GB → 单实例不够 → Cluster 3 分片
- 回源核算: 本地 90% 命中后剩 3k QPS 到 Redis; 未命中(过期+冷键)≈5%→150 QPS 落 MySQL,
  单个只读从库即可承接
```

### 第 3 步：写路径与 ID 发号器（§五分布式 ID 推演）
```
候选淘汰过程:
  - UUID v4: 32 字符违背"短"字; 无序导致 InnoDB 页分裂([[数据库原理与调优]]§三) ✗
  - 雪花算法: base62 后 11 字符可用 ✓ 但时钟回拨需处理、worker-id 分配要协调件
  - 号段模式: DB 每次批量取 1 万段内存分发 —— 实现最简, 重启浪费半段可接受 ✓
决策: 双号段缓冲(消耗至 20% 即异步预取下一段) + base62 → 6 位表达 568 亿
```

### 第 4 步：过载与故障预案（§四对照自查表）
| 故障 | 预案 | 触发阈值 |
|------|------|---------|
| 缓存雪崩(TTL 同刻到期) | 过期时间抖动 ±10%; 空值缓存防穿透 | 命中率 <85% 告警 |
| 发号 DB 抖动 | 号段双缓冲已吸收; DB 全挂 30min 内发号不中断 | 段余量 <20% |
| 热 key(明星转发单链) | 本地副本天然扛; 极端时 key 打散多副本 | 单 key >5k QPS |
| 整体过载 | 网关令牌桶限流; **保写降读**(写不可重试补偿成本高) | CPU>70% 或 P99>200ms |

### 第 5 步：复盘检查单
✓ 每层容量均有推导来源，无拍脑袋组件；✗ 未覆盖恶意刷量风控（面试必追问的诚实边界）；✗ 301 vs 302 的统计语义取舍——301 浏览器永久缓存会让点击统计失真，产品口径反过来影响技术选择。

> [!tip] 方法论沉淀
> 整题没有 Kafka、没有微服务、没有 K8s——**约束推导出的最简架构即最优架构**，与 [[架构设计与方案选型]] §二的 LogNet 推导同一思想。

## 七、待确认项

> ① 各消息队列（Kafka/RocketMQ/Pulsar）在百万 TPS 下的官方基准可比性；② Redis Cluster vs 代理分片模式的最新生产推荐；③ eBPF 在用户态限流观测中的落地成熟度。

> [!success] 残余复核（2026-09-13，联网核实）：② 已定论（官方口径层面），① ③ 仍开放。
> ② **已定论（以 Redis 官方文档为准）**：`Scale with Redis Cluster`（redis/docs 仓库 `content/operate/oss_and_stack/management/scaling.md`，2026-09-13 抓取）开篇即 "Redis scales horizontally with a deployment topology called **Redis Cluster**"，并给出部署推荐原文：**"the minimal cluster that works as expected must contain at least three master nodes. For deployment, we strongly recommend a six-node cluster, with three masters and three replicas"**；代理分片只出现在"从既有分片/客户端算法迁移"的语境里（"a sharding algorithm implemented by their client library or Redis proxy"）。结论：**官方推荐就是 Cluster（6 节点=3 主 3 从起）**，代理在官方文档里是历史/迁移形态而非并列推荐项；再往下的取舍（跨槽多键、客户端成熟度、运维工具链）应回到具体约束走 ADR（见 [[架构设计与方案选型]] §三）。注：本库 [[Redis原理与实践]] §八 待确认③（代理网关对跨槽 mget 的损耗口径）是这条的相邻未决项，属另一簇工作单。
> ① **仍开放**：MQ 百万 TPS 官方基准的可比性——判据=逐家记录「硬件规格 / 消息大小 / 分区数 / 持久化与确认配置 / 统计口径」，任一项不同即不可横向比；库内无更权威口径。
> ③ **仍开放**：eBPF 在用户态限流观测中的落地成熟度——判据=按内核版本列 BPF 特性（map 类型 / trampoline / CO-RE）与观测工具链的支持矩阵，并把"观测"与"限流执行"分开（本机是 Windows，无 eBPF 运行面，此项无法就地核验）。
