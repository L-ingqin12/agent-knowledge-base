# 音视频流媒体开发基础

> [!abstract] 定位
> 补齐本库缺失的音视频方向：编解码与封装的概念分层（H.264/AAC → FLV/MP4）、传输协议谱系（RTMP/RTSP/HLS/HTTP-FLV）、FFmpeg 处理管线（AVFormat→Codec→Filter→Swr/Sws）、播放器架构（ffplay 式三线程+音视频同步）、WebRTC 实时链路（SDP/ICE/DTLS-SRTP + 抗弱网三件套）。协议理论对照 [[计算机网络八股]]。

See also: [[CS-KB-Home]] · [[Linux高性能网络编程实战]] · [[高并发系统设计]] · [[LLM架构进阶-从注意力变体到推理引擎]]

## 一、概念分层：先分清五个"格式"

```
编码格式(codec): H.264/H.265(视频压缩算法)  AAC/Opus(音频)     ← 压缩"怎么算"
封装格式(container): MP4/FLV/TS/MKV                          ← 打包"怎么存"(含时间戳/索引/多轨)
传输协议: RTMP/RTSP/HLS/HTTP-FLV/WebRTC                      ← 搬运"怎么送"
渲染: SDL/OpenGL/AAudio                                      ← 呈现
```

**常见混淆正名**：MP4 不是编码是封装；"RTMP 直播"里跑的通常是 H.264+AAC；HLS 是把直播切成小 TS/fMP4 文件走 HTTP。

### H.264 分层压缩直觉
- **I 帧**自包含（关键帧，可独立解码=拖动锚点）、**P 帧**参考前一帧编码差值、**B 帧**双向参考——GOP 结构(I 间隔)直接决定起播延迟与容错半径
- 码率控制 CBR/VBR/CQP 的取舍：直播推流要稳(CBR 类)，点播要质量(VBR/CRF)。补到能直接抄命令（FFmpeg 官方 Encode/H.264 页的口径：通用场景推荐 **CRF 或 Two-Pass ABR** 两种模式）：
  1. **CRF 下要约束码率必须叠加 `-maxrate`/`-bufsize`**，否则 VBV 不生效（如 `-crf 23 -maxrate 3M -bufsize 6M`）
  2. 直播加 `-tune zerolatency` + **固定 `-g`/`-keyint_min`**（GOP 直接决定起播延迟与容错半径），并用 `-preset` 换编码耗时（`veryfast`→`medium` 是质量/CPU 的常见拐点）
  3. CQP 与 CRF **不是同义词**：CQP 逐帧固定量化参数、无质量自适应，同 QP 下码率随画面复杂度漂移
  4. 验收判据写成可测项：起播时间、卡顿率、码率方差、编码端延迟——各自定阈值后压测

> 来源：FFmpeg Encode/H.264 https://trac.ffmpeg.org/wiki/Encode/H.264
- NALU 与 Annex-B 起始码(00 00 00 01)：裸流 vs 封装内长度前缀的差异是解析崩溃高发点

## 二、传输协议选型表

| 协议 | 延迟 | 传输层 | 典型场景 | 备注 |
|------|------|--------|---------|------|
| RTMP | 1–3s | TCP | 推流入 CDN(事实标准) | 2020 后浏览器弃 Flash 仅存于 ingest |
| HTTP-FLV | 1–3s | TCP(HTTP 长连接) | 浏览器拉流(flv.js) | 复用 CDN/防火墙友好 |
| HLS | 6–30s | HTTP 切片 | 点播/iOS 兼容 | 延迟来自切片粒度; LL-HLS 可压到 ~2s(**待确认**各 CDN 支持度) |
| RTSP/RTP | <1s | RTP over UDP/TCP | 安防摄像头(ONVIF 生态) | 会话用 RTSP 控制, 媒体走 RTP |
| **WebRTC** | <500ms | UDP(SRTP) | 连麦/会议/云游戏 | 见 §五 |

## 三、FFmpeg 处理管线（libav 编程模型）

```
demux(avformat_read_frame)
   ├─ video packet(AVPacket=压缩数据+pts/dts)
   │     └─ decode(avcodec_send/receive) → AVFrame(YUV 像素帧)
   │            └─ sws_scale(色彩/尺寸变换) → 渲染(SDL_Texture/OpenGL)
   └─ audio packet ─ decode → AVFrame(PCM) ─ swr_convert(重采样) → 声卡回调
```

- 内存模型纪律：`av_packet_alloc/av_frame_alloc` 引用计数体系(ref/unref 成对)；帧数据按 CPU 对齐分配(与 SIMD 读齐宽，[[计算机组成原理]])——跨库传递未对齐帧=段错误或性能悬崖
- filter 图(`abuffer→volume→abuffersink`) 用字符串描述构图后逐帧推送——转码服务的水印/缩放/混音都长在这条轴上
- 命令行速查即管线直译：`ffmpeg -i in.mp4 -c:v libx264 -crf 23 -c:a aac out.m3u8` = 解封装→视频重编→音频重编→HLS 切片

## 四、播放器架构（ffplay 同构的四线程）

```
read_thread: demux 出 packet 按 stream 入 videoq/audioq(带容量限制防内存爆)
audio_thread / video_thread / subtitle_thread: 由 decoder_start(..., thread_name, ...) 创建的 3 个解码线程
             取包→解码→frame_queue(最多缓存3帧)
sdl_audio_callback: SDL_OpenAudioDevice 注册的声卡回调, 由声卡驱动拉取 PCM —— 音频是主时钟!
video_refresh: 主循环里调用的刷新函数(不是线程), 对照 audio_clock 校正视频呈现时机(超前 sleep/落后丢帧), 误差>阈值才硬同步
```

> [!warning] 更正（2026-09-13）：原写作「ffplay 同构的四线程：read_thread / video_dec_thread / audio_dev_thread / video_refresh」。与实际源码结构不符：`video_refresh` 是主循环里调用的刷新函数、**不是线程**；三个解码线程由 `decoder_start(..., thread_name, ...)` 创建，线程名为 `audio_thread`/`video_thread`/`subtitle_thread`（加 `read_thread` 共四个线程）；音频也不是"音频线程直接推声卡"，而是 `SDL_OpenAudioDevice` 注册的回调 `sdl_audio_callback` 拉取 PCM。照原文对照源码必然对不上。依据 ffplay.c 文件参考页（doxygen）函数/变量表 https://ffmpeg.org/doxygen/trunk/ffplay_8c.html

**音视频同步为什么让音频当主时钟**：人耳对声音断续极敏感(>50ms 可感，**经验值**，按场景实测校准)、视觉对丢帧宽容——以声卡消费速度为基准拉齐视频是体验最优解。同步策略三种(音主/视主/外部时钟)在 ffplay 里一个 av_sync_type 切换——工程上永远默认音主（ffplay 默认即 `AV_SYNC_AUDIO_MASTER`）。

- **视频落后时的处置顺序**：先丢帧（跳到下一帧）而不是 sleep 追帧（sleep 会让落后持续累积）；连续丢帧到阈值就向发送端请求关键帧——与 §五 的 PLI/FIR 对齐。

## 五、WebRTC：实时链路五件套

```
信令(SDP 交换媒体能力, 自定义通道 websocket 即可)
NAT 穿透(ICE 框架: STUN 探公网映射 / TURN 中继兜底 / 打洞优先)
加密(DTLS 握手换密钥 → SRTP 加密媒体)
传输(RTP+RTCP: 序列号/时间戳/丢包反馈)
抗弱网三件套:
  NACK    丢包重传(收端报告缺号, 发端补发)      — 治随机丢
  FEC     前向纠错(冗余包恢复)                 — 治持续丢, 带宽换可靠
  JitterBuffer 收端自适应缓冲(动态延迟抖动平滑) — 治乱序与抖动
拥塞控制: GCC/TCC 反馈带宽估计 → 动态调码率(联动编码器降分辨率)
```

**恢复链路还缺两件**（原三件套只覆盖收端反馈）：
- **关键帧请求 PLI / FIR**：解码器参考帧丢失、或新订阅者加入时，向发送端索要帧内编码帧——PLI（Picture Loss Indication）与 FIR（Full Intra Request）是 AVPF 的 Codec Control Messages（RFC 5104）
- **RTX 重传通道**：RFC 4588 规定重传包走**独立 RTP 流**（不同 SSRC/PT），需先协商才有地方补发；只实现"NACK 报缺号"会写出收到 NACK 却无处置的实现

| 症状 | 首选动作 | 延迟代价 |
|---|---|---|
| 随机丢包 | NACK → RTX 重传 | 约一个 RTT |
| 持续丢包 | FEC + 降码率 | 冗余带宽开销 |
| 参考帧丢失 / 新订阅者加入 | PLI / FIR 请求关键帧 | 约一个 RTT + 一帧编码时间（可能瞬时码率尖峰） |
| 乱序与抖动 | JitterBuffer 自适应深度 | 缓冲深度直接加在端到端延迟上 |

> 来源：RFC 5104（Codec Control Messages：FIR §4.3.1 与 PLI）https://www.rfc-editor.org/rfc/rfc5104.html ；RFC 4588（RTP Retransmission，重传走独立流）https://www.rfc-editor.org/rfc/rfc4588.html

- 与 RTMP 族的本质差：为**交互实时**(连麦对讲)设计，宁可降质不可攒缓冲；SFU(MCU 的进化)只转发不转码是主流拓扑(Janus/SRS/mediasoup)
- 回声消除 AEC/噪声抑制 NS 在采集侧(3A 算法)——连麦回声事故九成出在没走耳机且未开 AEC

## 七、待确认项

> ① WebRTC Insertable Streams(E2E 加密)在各 SFU 的支持进度；② AV1 实时编码在移动端的功耗表现；③ LL-HLS/LL-DASH 商用 CDN 覆盖率；④ ~~FFmpeg 7.x API 变更(ch_layout 重构)~~ → **新声道布局 API（`AVChannelLayout`）的分界点是 5.1**（`n5.0` 的 `channel_layout.h` 里 `AVChannelLayout` 出现 0 次，`n5.1` 才引入 `av_channel_layout_subset/compare/check`），7.x 只是后续承接移除旧字段；「7.x」这个版本号本身也已落后——当前最新发布为 8.1 "Hoare"（2026-03-16），上一版 8.0 "Huffman"（2025-08-22）。查 API 变更一律以 `doc/APIchanges` 为准。
