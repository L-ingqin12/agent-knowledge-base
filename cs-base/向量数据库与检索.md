# 向量数据库与检索

> [!abstract] 定位
> AI 基础设施纵深：从 embedding 到 ANN 检索的完整链路——相似度度量、HNSW/IVF/PQ 三大族机制级拆解、过滤难题、混合检索融合，以及产品谱系与容量估算。是 [[RAG检索增强生成实战]] 与 [[agent-memory-context-knowledge-design]] L3 记忆层的底层支撑。

See also: [[CS-KB-Home]] · [[深度学习算法基础]] · [[RAG检索增强生成实战]] · [[GraphRAG知识图谱增强实战]]

## 一、问题定义

```
文档/内容 --embedding模型--> d 维向量(384~3072)
查询 q 同样编码 → 找库中与 q 最近 TopK   (精确 KNN O(n·d) 不可行→ANN 近似)
```

- **度量必须匹配训练目标**：cosine(归一后等价内积 IP)/L2——用错度量=召回率无声崩塌
- 质量指标：recall@k（ANN 结果 vs 暴力搜索真值的重合率）× QPS × 内存三角权衡

## 二、ANN 三大族机制级

### 1. HNSW（分层可导航小世界图）
- 思想=跳表×近邻图：上层稀疏长边快速俯冲，**layer0 全量节点**短边精搜
- 参数：M(每点邻居数,典型16–48)/efConstruction(建图候选队列)/efSearch(查询候选队列，召回主旋钮)
- 优点：高 recall 下 QPS 最强族；缺点：内存大(n×d 向量 + n×M 邻接表)、删除靠墓碑标记、图遍历随机访问 cache 不友好

### 2. IVF（倒排文件+粗量化）
- k-means 聚 n 个向量为 √n 量级 centroid；查询先取最近 `nprobe` 个簇内暴力扫
- 需训练；簇边界丢召回 → nprobe 调高换时间

### 3. PQ 乘积量化（压缩轴）
- 把 d 维切成 m 段，每段 k-means 到 256 码本 → 每向量 m 字节（如 768 维 fp32=3072B，m=12 → 12B，压缩 **256×**；经典例子是 SIFT 128 维 / m=8：512B → 8B = 64×）
- ADC 用查表近似距离；OPQ 先旋转再切分降量化误差；常作为 IVF 的二级(PQ 内积表)组合成 IVF-PQ
- 代价：量化误差直接吃 recall → 必须带真值回归测试
- **两段式检索是工程必需**：① 用压缩码（ADC/二值）取 top-N（N≫k）；② 用原始 fp32 向量或残差编码对候选重排取 top-k——只做①不做②，量化误差会直接吃掉召回。召回验收判据写成「同一查询集上与暴力检索结果的重合率（recall@k 曲线）」，而非只看压缩比。

> [!warning] 更正（2026-09-13）：原写「768 维/12B ≈ 64×压缩」——算术错位：768×4B=3072B，压到 12B 是 **256×**；64× 是经典 SIFT(128 维)/m=8 的数字（512B → 8B）。
> 来源：https://raw.githubusercontent.com/pgvector/pgvector/master/README.md （Scaling 一节：二值量化 "with re-ranking for search"）

> [!tip] 组合拳与磁盘派
> 实战多为 IVF+PQ 或 HNSW+SQ 标量量化(int8)。十亿级单机放不下走 DiskANN/Vamana 磁盘图(SSD 随机读友好布局)。

### 2A. HNSW 插入与搜索伪码走读（把参数落到动作上）

**层数抽样——为什么是负对数**：
```
ℓ = floor( −ln(uniform(0,1)) × mL ),  mL = 1/ln(M)
```
均匀数取对数翻转后：大部分样本挤在 0 附近、少数拖长尾——恰好复刻跳表的几何分布（P(层≥k)=(1/M)^k）。M=16 时每上一层节点数≈÷16，log₁₆(n) 层即可覆盖亿级 → **俯冲路径 O(log n) 跳**。

**插入算法（Algorithm 1 精义）**：
```
INSERT(q):
  ℓ ← 抽样层; ep ← 入口点(全局)
  # 阶段1: 从最高层到 ℓ+1, ef=1 纯贪心 —— 只找"每层的最近点"当电梯井
  for lc ∈ [top..ℓ+1]:  ep ← GREEDY(ep, q, ef=1)
  # 阶段2: 在 ℓ..0 每层真搜索 + 建边
  for lc ∈ [ℓ..0]:
      W ← SEARCH-LAYER(q, ep, efConstruction)   # 候选队列：构建期宽度是 efConstruction，不是 M
      neighbors ← SELECT-NEIGHBORS-HEURISTIC(W, M)
      for e in neighbors:
          add_edge(q↔e);                      # 双向
          if degree(e) > M_max:               # 超容量裁剪
              prune(e 的邻居, 保多样性)
      ep ← W
```

> [!warning] 更正（2026-09-13）：原伪码写 `W ← SEARCH-LAYER(q, ep, ef=M)`——构建期层内搜索宽度是 **efConstruction**（hnswlib 还会把它钳到 `max(ef_construction, M)`），M 只决定选边数量与度上限。三者分工：M/M_max 管图结构与内存，efConstruction 管构建质量与耗时，efSearch 管查询召回与延迟。
> 来源：https://raw.githubusercontent.com/nmslib/hnswlib/master/hnswlib/hnswalg.h 、https://raw.githubusercontent.com/nmslib/hnswlib/master/README.md

**SELECT-NEIGHBORS 启发式（HNSW 比 NSW 强的核心）**：
候选按距 q 升序遍历，保留条件="比已选者都更接近 q"；若某候选更接近**已选的某个点**而非 q，则丢弃。效果：边不会扎堆在同一方向，图保持可导航性——这就是"启发式保多样性"，也是调 M_max 时召回不塌的结构保证。

**微例 trace**（2D, 插入 q=(5,5)，层抽到 1；现有 A(0,0)/B(10,10) 在层1）：
```
阶段1: 层1 GREEDY from A → dist(q,A)=7.07 < dist(q,B)=7.07? 相等取先到 → ep=A
阶段2: 层0 SEARCH ef=M 找到 {C(4,4), D(6,6), A, B...}
       SELECT: C 距 q=1.41 保留; D=1.41 但 D 是否更靠近 C? dist(D,C)=2.83 > 1.41 → 保留;
       B=7.07 且 B 更接近 D(5.66) < 7.07 → 弃 B ✓ (防止长边冗余)
```

**efSearch 召回数学直觉**：beam 宽度 ef 决定"贪心误入局部最优后被拉回的能力"。经验线：recall@10 ≥ 0.95 需 ef ≈ 10–20×K，再往上 QPS 线性掉——先测 recall 曲线再定参，不要拍。

## 三、过滤检索难题（工程最常见坑）

- **pre-filter** 先按属性筛再 ANN：图结构被切断→连通性崩、召回跌
- **post-filter** 先 ANN TopN 再筛：候选里可能没几个过筛→结果稀疏
- 成熟方案：把标量条件并入图遍历(过滤感知 HNSW)/双通道取并集重排/为高频过滤维度单独建集合级索引——各产品实现差异大，选型时必测自家过滤模式（最新学术方案 ACORN 等**待确认**成熟度）

## 四、混合检索与重排

```
BM25 关键词通道 ┐
                ├─▶ RRF 倒数排名融合 / 加权分数 ─▶ cross-encoder 重排 Top-k ─▶ 终榜
稠密向量通道    ┘
```

- 稀疏通道兜住专有名词/型号（embedding 弱项），稠密通道管语义改写
- RRF 公式 `Σ 1/(k+rank_i)` 免调权，k≈60 工程默认；重排器(cross-encoder)只对几十条精算，成本可控
- 本库映射：[[agent-memory-context-knowledge-design]] L3 的 wikilink 图谱+全文+向量三路混合即此范式；[[lognet-rootcause-multiagent-architecture]] 的 FTS5 通道对应 BM25 侧

## 五、产品谱系选型

| 层级 | 代表 | 定位 |
|------|------|------|
| 库 | FAISS / hnswlib / usearch | 嵌入自研，无服务化，GPU 支持看 FAISS |
| 关系库扩展 | **pgvector** / sqlite-vec | 复用现有 SQL 栈+事务+join 过滤；**千万级以内**最省心，到亿级必须走量化（halfvec/二值）+ 候选重排，或 Citus/PgDog 分片 |
| 专用引擎 | Milvus(存算分离/分段云原生)、Qdrant(Rust/负载过滤强)、Weaviate(模块化) | 十亿级/多租户/托管需求 |
| 搜索内核加列 | ES/OpenSearch dense_vector | 已有日志/搜索栈顺路加语义 |

> [!warning] 更正（2026-09-13）：pgvector 行原写「复用现有 SQL 栈+事务+join 过滤，亿级内首选省心」——与 §六「亿级 fp32 全量 HNSW 单机吃紧」自相矛盾，也超出官方口径：官方 Scaling 指引要求先用 halfvec / 二值量化并配候选重排，横向扩展另配 Citus/PgDog 分片；选型判据应是自家数据的 recall@k 与构建内存实测。
> 来源：https://raw.githubusercontent.com/pgvector/pgvector/master/README.md （Scaling / Monitoring 两节）

## 六、容量与成本速算

```
原始内存 ≈ n × d × 4B(fp32)      # 统一口径: 1 GiB = 2^30 B, 括号内为十进制 GB
10M × 768d = 28.6 GiB(30.7 GB)；int8 SQ 后 ≈7.2 GiB(7.7 GB)；PQ(m=24) ≈0.22 GiB(0.24 GB)+码本
HNSW 邻接表额外 ≈ n × M × 2 × 4B (M=32 时 10M≈2.4 GiB / 2.6 GB)
结论: 亿级 fp32 全量 HNSW 单机吃紧 → SQ/PQ 或 DiskANN 必选其一
```

> [!warning] 更正（2026-09-13）：原三行混用单位——「10M × 768d = 28.6 GB」实际是 28.6 GiB（=30.72 GB），而同一段的 PQ 0.24GB、邻接表 2.6GB 是十进制 GB，读者核算时对不上。现统一给出 GiB 与 GB 两个口径。
