## 二、TCP 核心八股

### 建拆连接
- **三次握手** SYN → SYN+ACK → ACK：双方各确认收发能力 + 同步初始序号 ISN（随机化防预测）
- 为何不是两次：防历史重复 SYN 造成脏连接；为何挥手四次：半关闭（FIN 后仍可收数据）
- **TIME_WAIT = 2MSL**：确保最后 ACK 达到+旧报文自然消亡；服务端大量 TIME_WAIT → `tcp_tw_reuse`/端口池/长连接化
- SYN Flood：syncookies 用加密序号免半连接队列占位

### 可靠性三支柱
1. **重传**：快重传（3 个 dup-ACK）优先于超时 RTO；SACK 报告乱序区块
2. **滑动窗口**：流量控制对端 rwnd；发送缓冲堆积即背压信号
3. **拥塞控制**：慢启动→拥塞避免(AIMD)→快恢复；CUBIC 默认（三次函数窗口增长）；BBR 测带宽×RTT 模型绕开丢包假设（Google 论文口径）

> [!tip] 排障映射
> 重传率/RTT 抖动看 `ss -ti`；本库代理链路诊断实操见 [[参考-网络路由与代理排障]]。

## 三、TLS 与 HTTPS

- **TLS 1.3 握手 = 1-RTT**（合并密钥交换+参数协商），0-RTT 恢复会话但有重放风险
- ECDHE 临时密钥→前向安全；证书链校验：签名逐级验至根 + 域名匹配 + 有效期 + 吊销（OCSP 装订优于实时查询）
- SNI 明文泄漏访问域名 → ECH 加密（部署度**待确认**）

> [!warning] 残余复核（2026-09-13，联网核实）：仍开放——"部署度"是动态数字，本轮只取回一个定点：Cloudflare 的 ECH 公告博文（`https://blog.cloudflare.com/announcing-encrypted-client-hello/`，页面 `datePublished` 2023-09-29，2026-09-13 抓取）讲清机制（ClientHello 拆内外两段，外层 SNI 不再泄漏真实域名）与首发时点，但**不含覆盖率数字**；标准侧 `draft-ietf-tls-esni` 的 datatracker 页面为脚本渲染，本轮未取到可引用的状态行。判据：① 覆盖率取 Cloudflare Radar 或厂商公开统计，并写死口径（按 zone 数还是按请求数）；② 客户端侧按版本核对 ECH 默认开启情况（Chromium/Firefox 各自 release notes 或平台状态页）；③ 标准侧以 `draft-ietf-tls-esni` 当前 rev 与状态为一手依据。三者缺一不得给出"部署度"结论。

## 四、HTTP 演进

| 版本 | 传输 | 关键特性 | 队头阻塞 |
|------|------|---------|---------|
| 1.1 (RFC 9112) | 文本/TCP | keep-alive、管线化（规范仍定义，见下注） | 应用层串行响应 |
| 2 (9113) | 二进制分帧/TCP | 多路复用、HPACK 头压缩、服务器推送（nginx 1.25.1 起已移除） | TCP 层丢包全体阻塞 |
| 3 (9114) | QUIC/UDP | 连接迁移(Connection ID)、内置 TLS1.3、0-RTT | 彻底解耦流间阻塞 |

WebSocket：HTTP Upgrade 升级后全双工帧协议——Agent 流式输出的常用通道（对照 [[opencode-pi-base-development-analysis]] SSE/WebSocket 选型节）。

> [!warning] 更正（2026-09-13）：HTTP/2 服务器推送不是"弃用中"而是**已被移除**——nginx 官方 CHANGES 原文「Changes with nginx 1.25.1 … Change: HTTP/2 server push support has been removed」，配套的 `http2_push`/`http2_push_preload` 指令随之消失（该特性 1.13.9 引入）；替代方案是 103 Early Hints 与 `Link: rel=preload`。（原表述为「服务器推送(弃用中)」）
> 来源：https://nginx.org/en/CHANGES

> [!warning] 更正（2026-09-13）：HTTP/1.1「管线化(废)」不准确——RFC 9112 §9.3.2 仍定义 pipelining 为合法行为（客户端 MAY pipeline，服务端 MAY 按序处理），沦为事实废条的只是主流浏览器/中间件不实现，实务按不启用处理。（原表述为「keep-alive、管线化(废)」）
> 来源：https://www.rfc-editor.org/rfc/rfc9112.html

## 六、机制推演四连（把八股讲成因果）

### 1. 为什么握手必须三次——完整状态机推演
两次握手的失败剧本：客户端发 SYN(s=100) 迟滞在网络 → 超时重发 SYN'(s=200) 建联完成通信关闭 → **旧 SYN 迟到抵达**服务端 → 若两握手则服务端单方面进入 ESTABLISHED 并等待数据 → 半连接悬挂+资源占用。三次的意义：服务端的 SYN+ACK 需要**第三次 ACK 确认双方序列号共识**，旧 SYN 的确认会被客户端 RST 掉。ISN 随机化另防序号预测注入。

### 2. TIME_WAIT 洪峰处置矩阵
| 手段 | 语义 | 风险 |
|------|------|------|
| 连接池/长连接 | 从源头减少短连接 | 根治首选 |
| `tcp_tw_reuse=1` | 出站复用需时间戳窗口校验 | 仅客户端方向安全 |
| `tcp_max_tw_buckets` | 上限强制回收 | 超 bucket 直接砍，激进 |
| SO_LINGER=0 强制 RST | 跳过四次挥手 | 破坏优雅关闭，慎用 |
服务端大量 TIME_WAIT 本质是"谁先主动关"问题——让客户端先关是架构解。

### 3. Nagle × 延迟 ACK：40ms 卡顿经典案发
发送端 Nagle 攒小包等 ACK；接收端延迟 ACK 等 ~40ms 才回。两侧同时启用 → 写小包应用(如逐条 RPC/游戏帧)出现固定周期卡顿。解法：实时性 socket 关 Nagle(`TCP_NODELAY`)，或应用层攒批。

两侧对账（排障时两边都要看）：

| 侧 | 开关 | 语义 | 依据 |
|----|------|------|------|
| 发送端 | `TCP_NODELAY` | 关 Nagle，小包立即发 | 应用层 `setsockopt` |
| 接收端 | `TCP_QUICKACK`（Linux 2.4.4+） | 置位后立即回 ACK 而不再延迟；**该标志非永久**，后续 TCP 处理会重新进入/退出 quickack 模式，排障脚本常需反复置位 | tcp(7) 手册 |

- 观测点：`ss -ti` 看 rtt/rto/ato 与重传计数；抓包确认是否出现"小包等待 + 延迟 ACK"的 ~40ms 周期
- 收窄一处：`TCP_QUICKACK` 的生效窗口在 tcp(7) 中**没有**"仅在收到数据之后"的原文表述，按手册口径表述为"非永久、会被后续处理重置"
- 关 Nagle 不是万能：大包本就与 Nagle 无关；小包风暴的正解仍是应用层攒批/消息合并
> 来源：https://man7.org/linux/man-pages/man7/tcp.7.html

### 4. TLS 1.3 握手密钥推导表（1-RTT 全过程）
```
ClientHello(key_share=ECDHE公钥, supported_versions)
  → ServerHello(key_share) + {EncryptedExtensions} + {Cert, CertVerify} + {Finished}
     ← 双方 HKDF 链: 提取(ECDHE共享密钥) → 派生 handshake keys → 加密此后一切
  ← client Finished(1-RTT 完成)
0-RTT: early data 用 resumption secret 提前发 —— 无防重放, 仅幂等请求可用
```
前向安全来源=ECDHE 临时私钥一次性；证书验证在加密信道内进行（1.2 明文的改进）。

## 七、待确认项

> ① ECH 全球部署覆盖率动态变化；② BBR v2/v3 公平性争议的最新社区结论；③ QUIC 在企业中间盒环境的穿透成功率统计口径。

> [!success] 残余复核（2026-09-13，联网核实）：② 已定论（出处与状态落定），① ③ 仍开放。
> ② **已定论**：BBR 的争议已从"社区讨论"转入标准化流程——IETF 已有工作组草案 **`draft-ietf-ccwg-bbr`（当前 -06，标题 "BBR Congestion Control"，Intended status: Experimental，署名侧 Google，Expires 2027-01-07）**，草案正文含 fairness / convergence 相关讨论（2026-09-13 抓取 datatracker 文档页 https://datatracker.ietf.org/doc/draft-ietf-ccwg-bbr/ ）。即：**v2 未独立标准化，v3 走 IETF CCWG**；要引"最新结论"应引该草案与 CCWG 会议材料，而不是引博客争论。若要给实质结论，判据=读该草案的公平性/收敛性章节并摘出"与其他 CCW 共存的量化要求"（本轮只落定出处，未读该章节）。
> ① **仍开放**：见 §三 复核（动态指标，需 Cloudflare Radar / 厂商统计 + 客户端默认情况两路交叉，缺一不可）。
> ③ **仍开放**：QUIC 在企业中间盒环境的穿透成功率——本机与库内均无统计口径。判据：先写死三件事再谈数字——中间盒定义（UDP 阻断 / 仅 443 放行 / TLS 检查）、样本来源（厂商遥测 vs 独立测量论文）、时间窗；三者任一缺失即不可比。
