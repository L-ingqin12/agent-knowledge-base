# 数据库原理与调优

> [!abstract] 定位
> 从存储引擎到查询优化的完整纵深：基础模型 → B+/LSM 引擎对决 → 索引/MVCC/WAL 机制级拆解 → 系统化调优方法 → SQLite 实战调优（附本库 LogNet PoC 真实基准）。目标：不止答对八股，还能在 EXPLAIN 和 PRAGMA 层面动手。

See also: [[CS-KB-Home]] · [[操作系统八股]] · [[高并发系统设计]] · [[lognet-rootcause-multiagent-architecture]]

## 一、执行一条 SQL 发生了什么

```
连接器(鉴权/连接池) → 分析器(词法语法) → 优化器(代价模型选计划)
  → 执行器(火山式迭代器逐行拉取) → 存储引擎(InnoDB/…) → Buffer Pool → 磁盘
```

- **代价模型**：扫描成本 × 选择率估算；估算依据=索引基数(statistics/distinct)，统计过期→计划劣化（`ANALYZE` 修复）
- 火山迭代器优点抽象统一，缺点虚调用频繁——列存引擎改向量化批处理（DuckDB/ClickHouse 路线）

## 二、存储引擎两大流派

| 维度 | B+ 树（InnoDB/SQLite） | LSM 树（LevelDB/RocksDB/LSMT 系列） |
|------|------------------------|-------------------------------------|
| 写路径 | 原地更新+随机写 | 内存 memtable→顺序刷盘 SST |
| 读路径 | 树高 3~4 次 IO 内定案 | 逐层查找+ bloom 过滤，读放大 |
| 放大特性 | **写放大**高（原地改页+日志） | 读放大/空间放大（多版本重叠），靠 compaction 摊 |
| 适用 | 读多写少、强事务 OLTP | 写吞吐优先（日志流/时序）、后台 compaction 可控 |

> [!tip] 选型直觉
> 点查为主+事务强一致 → B+ 族；写洪峰+允许最终合并 → LSM 族。LogNet 日志入库属"批量写一次、多次点查/全文查"，PoC 选 SQLite(B+) 且用 executemany 把随机写压成事务内顺序写——正是绕开 B+ 写放大的经典手法。

## 三、索引机制级

### B+ 树结构性质
- 聚簇索引=主键树叶子即整行；二级索引叶子存主键值 → **回表**
- 页 16KB(InnoDB 默认)；分裂自中间记录，**自增主键顺序插入免页分裂碎片**，UUID 主键=随机写灾难
- 高度公式感：千万行 ≈ 3 层（扇出 ~1200），3 次 IO 定位

### 高效使用索引（进阶清单）
1. **最左前缀**：联合索引(a,b,c) 支持 a / ab / abc；跳 a 全废
2. **覆盖索引**：查询列全在索引内免回表——高频 SELECT 列做进联合索引尾部
3. **索引下推 ICP**：where 条件在引擎层先过滤再回表，减少回表次数
4. **前缀索引**：长字符串取前 N 位（区分度=`COUNT(DISTINCT prefix)/COUNT(*)` 达标即可）
5. **失效场景**：对索引列函数运算/隐式类型转换(字符串列传数字)/前导 `%like`/OR 混合无索引列
6. 排序利用索引有序性避免 filesort；GROUP BY 同理

## 四、事务与 MVCC（机制级）

### 隔离级别 × 异常矩阵

| 级别 \ 异常 | 脏读 | 不可重复读 | 幻读 |
|------------|------|-----------|------|
| Read Uncommitted | ✗有 | ✗有 | ✗有 |
| Read Committed | ✓防 | ✗有 | ✗有 |
| Repeatable Read(InnoDB 默认) | ✓ | ✓ | 基本✓* |
| Serializable | ✓ | ✓ | ✓ |

*InnoDB RR 下快照读靠 MVCC 免幻读；**当前读**(for update/update) 靠临键锁(next-key=记录+间隙) 锁住范围。

### MVCC 实现（InnoDB 口径）
- 每行隐藏列 `trx_id`(最后修改者) + `roll_pointer`→undo 版本链
- ReadView={活跃事务列表}：沿版本链找第一个满足可见性的版本——RC 每次 SELECT 新建 ReadView，RR 复用首次 → 这就是两级隔离的实现差
- 旧版本由 undo 提供，长事务阻止 purge → **版本链膨胀是长事务头号罪状**

### 日志与崩溃恢复
- **WAL 铁律**：先写日志后改数据页。redo(物理,保证持久性) / undo(逻辑,保证原子性+供 MVCC)
- 提交流程：写 redo buffer→fsync(binlog 两阶段提交防主从不一致)→commit 标记
- 检查点(checkpoint)：推进刷脏水位，缩短恢复重放长度
- 崩溃恢复：redo 重放至最近 checkpoint → 未提交事务用 undo 回滚

## 五、锁与死锁

- 行锁三态：record/gap/next-key；唯一命中退化为 record lock
- 死锁：InnoDB wait-for 图主动检测回滚代价小者；应用侧兜底=锁排序+小事务+超时参数
- 乐观锁（version CAS）适合低冲突长尾业务；悲观锁适合热点竞争

## 六、系统化调优方法（不是玄学清单）

```
0. 定义 SLO: P99 延迟/QPS 目标 → 有靶才能调
1. 定位: slowlog 抓 Top → EXPLAIN 看 type(key rows Extra)
   - type 优劣序: const > eq_ref > ref > range > index > ALL
   - Extra 危险词: Using filesort / Using temporary
2. SQL 改写优先于加机器: 索引覆盖/分页 keyset/OFFSET 大翻页改 WHERE id > last
3. 结构层: 冷热分离/归档表/分区(partition 裁剪需带分区键)
4. 实例层: buffer pool 命中率、脏页比例、redo fsync 等待、连接池上限(≠越大越好, 上下文切换反噬)
5. 系统层: 文件系统 fsync 语义、NUMA 亲核、磁盘队列深度
6. 每次只动一个变量并回归基准 —— 否则归因失效
```

## 七、SQLite 进阶实战（本库 LogNet PoC 实证）

| 调优项 | 做法 | 本库实测/依据 |
|--------|------|--------------|
| WAL 模式 | `PRAGMA journal_mode=WAL` | 读写不互斥；checkpoint 由 wal_autocheckpoint 兜底。**前置条件**：`-wal`/`-shm` 必须与主库同机同目录——VFS 需提供 `xShmMap/xShmLock/xShmBarrier/xShmUnmap` 共享内存原语，网络文件系统/跨节点共享卷不可用；无共享内存时只能 `locking_mode=EXCLUSIVE` 降级（且只要 journal mode 为 WAL 就一直保持 EXCLUSIVE） |
| 持久性档位 | `synchronous=NORMAL` | WAL 下 NORMAL 只在 checkpoint fsync——掉电丢最近事务但**不损坏库**（此结论需版本前提，见下）；FULL 每事务 fsync 吞吐骤降。LogNet 为分析型负载选 NORMAL，属正确取舍 |
| 批量写 | 单事务包 executemany | 万级行单事务 ≈ 每行独立事务数百倍差距（fsync 次数决定论）；PoC 291,725 行折叠入库秒级完成 |
| 分页 | **keyset**: `WHERE id > ? LIMIT n` | OFFSET n 需扫过前 n 行；PoC PAGE_SIZE=50_000 全量导出线性时间 |
| 全文检索 | FTS5 倒排 | 分词→倒排表(segment)；**语料语言 → 分词器**：unicode61(默认，Unicode 6.1 词边界，对中日文这类无空格语言不切词)/ porter(英文词干化，叠在 unicode61 外层)/ trigram(中文与子串检索)，更换分词器需重建索引；查询 P50=12.7ms / P95≈348ms @291k 行（bench_fts_p95 实测，guard<500ms）；外部内容表(contentless 选项)省一份原文存储（两个选项的区别见下） |
| 尾延迟治理 | WAL checkpoint 抖动 + 冷页 | P95 尾巴主要来自 auto-checkpoint 合并与页缓存未热——分析型场景可在空闲窗手动 `PRAGMA wal_checkpoint(TRUNCATE)` |

> [!info] 与项目的关系
> 以上 SQLite 条目全部对应 [[lognet-rootcause-multiagent-architecture]] M0 PoC 的真实实现（scripts/lognet-poc），数字来自 tests/bench_fts_p95.py——调优结论以本项目复现实验为据，非转抄。

> [!warning] 更正（2026-09-13）：WAL 的"不损坏库"必须加**版本前提**——SQLite 官方 WAL 文档 §11「The WAL-Reset Bug」：该缺陷「likely present in all version of SQLite from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09)」，已在 **3.51.3 (2026-03-13)** 修复，另有 **3.44.6 / 3.50.7** 回移版。故验收判据要加 `sqlite_version` 断言（≥3.51.3 或回移版）与 `PRAGMA integrity_check` 回归。（原表述为「掉电丢最近事务但不损坏库」，未带版本前提）
> 来源：https://sqlite.org/wal.html

> [!warning] 更正（2026-09-13）：「外部内容表(contentless 选项)」把两个不同选项混成了一个——`content=外部表名` 是 **External Content Table**（原文留在自己的表里，索引不重复存，仍可读列值）；`content=''` 是 **Contentless Table**（完全不存原文，因而**不能再读列值**，更新/删除需特殊处理，另有 contentless-delete 变体）。"省一份原文存储"要写清是哪一类、各自能/不能做什么。（原表述为「外部内容表(contentless 选项)省一份原文存储」）
> 来源：https://sqlite.org/fts5.html

> FTS5 分词器出处（含上表"语料语言 → 分词器"一行）：https://sqlite.org/fts5.html

> - **Percolator 血统的「命名」差异本身就值得记**：TiDB 官方文档**明确自述** "To support distributed transactions, TiDB adopts two-phase commit (2PC) in optimistic transactions."，并在 PD 文档里写 TSO "crucial for **enabling the Percolator model** within TiDB"；而 **PolarDB-X 官方文档全篇不出现 `Percolator` 一词**（把取到的各主题页与阿里云帮助页全文检索，零命中）——两家定位方式不同，对比时应按能力而非按名号。
> - **① 事务模型的层次不同（关键差异一）**：
>   - TiDB：**悲观模式自 v3.0.8 起为默认**（"Starting from v3.0.8, newly created TiDB clusters use the pessimistic transaction mode by default."），但其悲观事务**建在乐观（Percolator）模型之上**（"optimistic transactions are the basis for pessimistic transactions"）——即**行锁是叠加在 Percolator 之上的**，与教科书 Percolator「无行锁、靠写冲突检测」不同。
>   - PolarDB-X：提供**可选择的** `TRANSACTION_POLICY`（**`XA` | `TSO` | `TSO_READONLY`**）——**XA 模式是 TiDB 没有的**；多分区写入走 2PC，且文档承诺「即便事务提交过程中发生节点宕机，基于 2PC 的事务恢复机制也能确保原子性」。
> - **② ts 分配点不同（关键差异二）**：
>   - TiDB：`start_ts`/`commit_ts` 均取自 **PD**——"TiDB gets a timestamp … from PD as the unique transaction ID … called `start_ts` … TiDB receives a commit version number from PD and marks it as `commit_ts`"；TSO 由 46 位物理 + 18 位逻辑构成、全局单调。TiDB 官方**自己把「需要一个集中式授时服务」列为缺点**（"In need of a centralized timestamp allocation service"）。
>   - PolarDB-X：同样是**中心授时**，但**授时方是 GMS**，且是**独立 Paxos 三节点高可用服务、CN 经 RPC 获取**——"PolarDB-X元数据服务（GMS）基于Paxos共识协议提供一个具备三节点高可用性的服务，PolarDB-X的计算节点（CN）会通过RPC接口和元数据服务（GMS）进行通讯并获取全局时钟"。即：**Percolator 原版把时间戳取自存储层，这两家都改成了独立的集中授时服务，且 PolarDB-X 的授时服务有明确的共识/HA 形态**。
> - **③ 提交优化路径（关键差异三，TiDB 侧最可核）**：TiDB 有两级减负，且**默认开**——`tidb_enable_1pc`（**默认 ON，仅对新集群**；仅对只影响单个 Region 的事务生效）与 `tidb_enable_async_commit`（**默认 ON，仅对新集群**；把 2PC 第二阶段异步化）；二者叠加时可**不需要向 PD 取时间戳**从而降低提交延迟，代价是**只保证因果一致而非线性一致**（`tidb_guarantee_linearizability` 默认 ON 时才回 PD 取 TS 保证线性一致；置 OFF 则跳过该次 PD 往返、只剩因果一致）。**「默认 ON 只对新集群生效，升级来的集群仍是 OFF」**是迁移时最容易踩的默认值陷阱。
> - **④ 源码级生效前提（把「默认开」落到条件上）**：TiDB 的提交实现**已不在 `pingcap/tidb` 仓**（该仓 master 树中无 `2pc.go`），而在 **`tikv/client-go`** 的 `txnkv/transaction/2pc.go`：`checkAsyncCommit()` 在 `hasSharedLocks`、事务作用域非全局、键数超 `KeysLimit`、累计键体积超 `TotalKeySizeLimit`、需写 binlog 时返回 false；`checkOnePC()` 在 `hasSharedLocks`、非全局作用域、设了 `commitTSUpperBoundCheck` 时返回 false；并有 `needLinearizability() = !causalConsistency`，注释点明 "Async commit is not compatible with Binlog because of the non unique timestamp issue"。即「默认开」≠「一定走」，是否走由运行期条件决定。
> - **⑤ GSI 与事务的关系（PolarDB-X 侧）**：官方 GSI 文档写明 "PolarDB-X使用分布式事务维护主表和索引表之间数据强一致"——即 GSI 的强一致由分布式事务兜底，这是与「本地二级索引」的关键分野。
> 依据：https://docs.pingcap.com/tidb/stable/optimistic-transaction ；https://docs.pingcap.com/tidb/stable/pessimistic-transaction ；https://docs.pingcap.com/tidb/stable/transaction-overview ；https://docs.pingcap.com/tidb/stable/system-variables ；https://docs.pingcap.com/tidb/stable/tso ；https://github.com/tikv/client-go/blob/master/txnkv/transaction/2pc.go ；https://doc.polardbx.com/zh/features/topics/distributed-transaction.html ；https://doc.polardbx.com/zh/operator/faq/16-transaction-strategy.html ；https://doc.polardbx.com/zh/features/topics/gsi.html （取回于 2026-09-13）
