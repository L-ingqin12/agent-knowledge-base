## 一、创建族

### 1.1 Builder：什么时候它不是过度设计

**触发信号**：构造参数 >4、多数可选、存在"非法组合需要在构造期拒绝"。两三个字段的 struct 配 builder 是 YAGNI——C++20 聚合初始化已够用：

```cpp
struct ServerOpts {          // 简单场景的终点：designated initializers
    std::string host = "127.0.0.1";
    int         port = 8080;
    bool        tls  = false;
};
ServerOpts s{ .host="10.x.x.x", .port=443, .tls=true };   // 完事，无需 builder
```

**真正需要 builder 的场景**：不变量校验 + 分步装配。关键技巧是"build() 收口时才校验"，让中间态不可被误用：

```cpp
class ConnBuilder {
    std::optional<std::string> host_;
    std::optional<int> port_;
public:
    ConnBuilder& host(std::string h) { host_ = std::move(h); return *this; }
    ConnBuilder& port(int p)         { port_ = p; return *this; }

    // 唯一的出口做全量校验 —— 非法组合在这里死掉, 而不是运行期深处
    std::expected<Conn, Err> build() {
        if (!host_ || !port_)            return std::unexpected(Err::MissingField);
        if (*port_ <= 0 || *port_ > 65535) return std::unexpected(Err::BadPort);
        return Conn{*host_, *port_};
    }
};
auto c = ConnBuilder{}.host("db.internal").port(5432).build();  // expected<Conn,Err>
```

**推理链**：为什么返回 `expected` 而非抛异常？构造路径在启动热区，异常控制流会打乱初始化顺序审计；`expected` 让调用方**语法上无法忽略失败**（不解包就用不了）。为什么链式返回引用而非值？避免移动开销且允许派生 builder 继续链。

**事故现场**（不用 builder 的代价）：某网关把 11 个构造参数按位置传——第 7/8 个同为 bool，上线即接反超时开关；排查半天定位到调用点。builder 的命名方法让这类错误在 review 里一眼可见。

### 1.2 单例：Meyers 形态为什么线程安全，以及何时仍不该用

```cpp
Logger& Logger::instance() {
    static Logger inst;      // C++11 起魔法静态: 并发首次调用保证只初始化一次且线程安全
    return inst;
}
```

- **机制**：C++11 [stmt.dcl]/4 规定局部 static 初始化并发安全——编译器生成守卫变量 + 双检查（GCC 用 guard acquisition，等价 futex 快慢路径，见 [[LibC运行时排查-TLS与锁]] §三）
- **该保证可以被实现关掉**：GCC/Clang 的 `-fno-threadsafe-statics` 不发射 C++ ABI 指定的线程安全初始化代码（嵌入式/体积敏感项目常开）——在该前提下本段断言失效，Meyers 单例不再线程安全
- **验收判据**：用 TSan 跑"多线程并发首次调用 `instance()`"应无报告；若构建带了 `-fno-threadsafe-statics`，该测试**必须失败**——反过来用它证明保证确实被关掉了

> [!note] 段号说明（2026-09-13）：引用的「C++11 [stmt.dcl]/4」无误——N3337（C++11 文本）中该规则确在 /4（https://timsong-cpp.github.io/cppwp/n3337/stmt.dcl ）；现行草案把它放在 /3（https://eel.is/c++draft/stmt.dcl ），草案段号变动不改写历史版本引用，故此处**不改段号**。依据补充：GCC `-fno-threadsafe-statics` 说明 https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Dialect-Options.html
- **仍然不要滥用的两个硬理由**：
  ① 测试污染：单例状态跨测试存活，用例顺序依赖是 flaky test 头号来源——需要全局资源时，正确姿势是 main 组装一次后**构造注入**传递
  ② 销毁次序黑洞：多个单例互相引用时析构顺序未定义，退出期悬垂调用（同 [[LibC运行时排查-TLS与锁]] §一 atexit 黑洞同源）
- **保留判据**：日志器/进程指标注册器这类"真·进程唯一基础设施"可以单例；一切业务服务一律注入

### 1.3 对象池：和分配器的边界

池化只在 **创建昂贵**(TCP/TLS 握手、进程句柄) 或 **需要确定性延迟**(实时路径禁 malloc) 时成立。普通对象交给分配器 size-class 缓存即可（jemalloc/tcmalloc 已是"隐式池"，[[LibC与动态链接]] §六）。自建池的三件套：RAII 归还句柄（防泄漏）、最大容量+淘汰（防膨胀）、健康检查（借出前 ping，防僵尸连接）。

## 二、结构族

### 2.1 装饰器：正交能力的组合爆炸终结者

需求演化剧本：HTTP client → 要重试 → 要限流 → 要 metrics。继承路线 `RetryingThrottledMeteredClient` 三层后每加一维翻倍。装饰器把维度拆开：

```cpp
struct IClient { virtual Resp send(const Req&) = 0; virtual ~IClient() = default; };

template <std::derived_from<IClient> Inner>
struct RetryClient : IClient {
    explicit RetryClient(Inner inner, int tries) : inner_(std::move(inner)), tries_(tries) {}
    Resp send(const Req& r) override {
        for (int i = 1;; ++i) {
            try { return inner_.send(r); }
            catch (TransientError&) { if (i == tries_) throw; /* 指数退避略 */ }
        }
    }
private: Inner inner_; int tries_;
};
// 组装点一目了然, 顺序本身是策略:
IClient& c = Metered{ Throttled{ Retry{ Base{}, 3 }, 100 }, registry };
```

**推理链**：模板版零虚调用开销但组装期定型；运行期动态装配（插件加载顺序）则退回 `unique_ptr<IClient>` 装饰。两者接口相同——先用模板，出现运行期组装需求再降级到指针版。

### 2.2 外观（Facade）：SDK 封装层的纪律

五步子系统流程收口为一个方法时，Facade 的唯一纪律是**不做业务判断**——它只编排顺序与转译错误。一旦 Facade 出现 if 分支做策略选择，说明该抽出的其实是 Strategy。本库 [[opencode-pi-base-development-analysis]] 的基座 SDK 封装层就是此边界案例的活样本。

## 三、行为族

### 3.1 观察者：悬垂回调事故解剖（必读）

裸观察者的经典崩溃：

```cpp
struct Bus { vector<Callback*> subs; void emit(Ev e){ for(auto*c:subs) (*c)(e);} };
struct Worker { Worker(Bus& b){ b.subs.push_back(&cb); } Callback cb; };
// Worker 先于 Bus 析构 → Bus.emit 跳进已析构对象 → 随机崩溃, 且仅在高负载时偶现
```

**根因**：主题持有裸指针=对观察者生命周期的隐式假设。修复三代方案，按健壮度递增：

```cpp
// 方案A: 手动退订 —— 纪律依赖, 忘记即雷
struct Worker { ~Worker(){ bus.unsub(handle); } SubHandle handle; };

// 方案B: weak_ptr 探活 —— 主题侧自动跳过死亡观察者
for (auto& w : subs) if (auto sp = w.lock()) (*sp)(e);

// 方案C(推荐): 句柄式订阅, RAII 自动退订 —— 订阅即拿票, 析构即退票
struct Subscription {
    Bus* b; uint64_t id;
    Subscription(const Subscription&)             = delete;  // 隐式拷贝 = 两份析构 → 两次 unsub
    Subscription& operator=(const Subscription&)  = delete;
    Subscription(Subscription&& o) noexcept : b(o.b), id(std::exchange(o.id, kInvalidId)) {}
    ~Subscription(){ if (id != kInvalidId) b->unsub(id); }   // 对未知/已退订 id 幂等
};
auto sub(Bus&, Fn) -> Subscription;
```

- 两个边界补全（否则"推荐方案"会变成新的重复释放源）：
  1. **句柄自身的拷贝/移动语义**：有隐式拷贝构造时，两份拷贝析构会对同一 `id` 调两次 `unsub`——可能误删他人订阅或踩已回收槽位。要么显式 `delete` 拷贝、只保留移动（移动后把 `id` 置无效），要么把 `id` 换成 `weak_ptr`/代际号做二次校验，并让 `unsub` 对未知 id 幂等
  2. **回调中增删订阅导致迭代器失效**：最小复现是订阅者在 `emit` 回调里 `unsub` 自己（容器被就地改写，正在迭代的迭代器失效）；修复是**分发前拷贝订阅快照** + 用 `id` 而非指针比对

> 依据：三/五/零法则（管理资源句柄的类不应使用隐式定义的特殊成员函数）https://cppreference.cn/w/cpp/language/rule_of_three

**推理链**：方案 B 的 lock() 有竞态窗口（探活后、调用前对方析构）——单线程事件循环内无害，多线程需主题持 shared_ptr 或加代际验证。**选型口诀：跨线程广播→C(RAII 句柄)+主题端队列拷贝快照后再分发**（避免回调中增删订阅导致迭代器失效——第二个隐藏炸弹）。

### 3.2 状态机：从 enum+switch 到显式转移表

信号：`if (state == X && event == Y)` 散落三处以上。升级路径：

```cpp
enum class St { Idle, Running, Paused };
enum class Ev { Start, Pause, Resume, Done };

struct Transition { St from; Ev on; St to; };      // 转移规则即数据
static constexpr std::array<Transition, 4> transitions{{
    {St::Idle,    Ev::Start,  St::Running},
    {St::Running, Ev::Pause,  St::Paused },
    {St::Paused,  Ev::Resume, St::Running},
    {St::Running, Ev::Done,   St::Idle   },
}};
// 原写法（编译不过，勿抄）：
//   std::pair{St::Idle, Ev::Start, St::Running}
//   ← std::pair 只有 first/second 两个成员，三个实参既无匹配构造函数也无 deduction guide，
//     结构化绑定也不能用三个名字解构 pair
constexpr std::optional<St> next(St s, Ev e) {
    for (auto& [a, ev, b] : transitions) if (a == s && ev == e) return b;
    return std::nullopt;                       // 未定义转移在此显式拒绝
}
```

> [!warning] 更正（2026-09-13）：原文用 `std::pair{St::Idle, Ev::Start, St::Running}`（四行同样写法）配 `for (auto& [a, ev, b] : transitions)`，这段**编译不过**。`std::pair` 按定义只有 `first`/`second` 两个成员，三个实参既无匹配构造函数、也无 deduction guide，结构化绑定也不能用三个名字解构 pair（本机 clang 22 `-std=c++20 -fsyntax-only` 复现：no viable constructor or deduction guide for deduction of template arguments of 'std::pair'）。已改为 `struct Transition` + `std::array<Transition,4>`（等价方案：`std::tuple`）。front-matter 承诺「全部代码为可直接编译骨架」，本文目前**尚未接 CI 真编译**，属待办。

> [!note] 残余复核（2026-09-13，本机实测）：上面提到的「本文尚未接 CI 真编译」仍是待办，但本轮至少把**修正后的 §3.2 片段**在本机 clang **22.1.0-rc3** 上过了一遍：`clang++ -std=c++20 -fsyntax-only` 与 `-std=c++26 -fsyntax-only` 均通过，且 `-std=c++20` 下可编译并运行（`next(St::Idle, Ev::Start)` 返回有值）。收口该待办的判据：把各节可独立编译的片段抽成 `snippets/*.cpp`（未定义的 `Conn`/`Err`/`Callback` 等补最小桩），加一条 `-std=c++20 -fsyntax-only` 门禁进 CI，让 front-matter 的「可直接编译骨架」变成可回归断言。

收益：转移规则成为**数据**——可以打印全表做评审、可以断言可达性、新增迁移零散弹。复杂守护条件再加 action 回调列；更上层直接换 Boost.Sstatechart/MSMF。本库 [[state-machine-quality-gate-loop]] 的 7 状态门控即此模式的工程化版本。

### 3.3 Visitor 之死与 variant 重生

传统 double-dispatch 需要 accept+visit 类树。C++17 后：

```cpp
using Node = std::variant<Num, Add, Mul>;
struct Eval {
    double operator()(Num const& n) const { return n.v; }
    double operator()(Add const& a) const { return eval(a.l)+eval(a.r); } // 递归略
    double operator()(Mul const& m) const { return eval(m.l)*eval(m.r); }
};
double eval(Node const& n) { return std::visit(Eval{}, n); }
```

新增操作=加一个仿函数（variant 路线强项）；新增类型=改 variant 定义并让 visit 的 exhaustive 匹配在编译期报错——**类型集合稳定、操作频繁增长**时完胜类层次 Visitor；反之（操作稳定、类型狂加）仍选经典虚函数树。这是"数据 vs 操作哪个封闭"的一线之隔，面试常考的实质。

## 四、模式如何被语言吸收（演化视角）

| 传统模式 | 被什么吸收 | 残留场景 |
|----------|-----------|---------|
| Command | `std::function`+闭包捕获上下文 | 需要撤销栈/meta(命令名)时仍是类 |
| Strategy | 模板参数(编译期)/function(运行期) | 策略带多方法协议时才立接口 |
| Iterator | range-for / Ranges 视图 | 自定义惰性序列仍手写 sentinel |
| Visitor | variant+visit+overloaded | 开放类集合 |
| Singleton | DI 容器/模块级实例 | 真·进程唯一基础设施 |

**总判据一句话**：好模式的引入应当让代码总量下降或直线度上升；为模式而生的类层次是反向重构。评审时问一句"删掉这个抽象层会发生什么坏事？"答不出就删。

## 五、待确认项

> ① Chromium/LLVM 级代码库的模式使用率实证统计口径；② C++26 反射落地后 serialization/Visitor 族模式的最终形态；③ 协程普及对 Callback/Observer 族在 IO 层的替代进度。

> [!success] 残余复核（2026-09-13，联网核实）：② 已定论（编译器侧进度可查），① ③ 仍开放。
> ② **已定论**：cppreference 的 C++26 编译器支持表（https://en.cppreference.com/w/cpp/compiler_support/26 ，2026-09-13 抓取）显示 **Reflection（P2996R13 · P3096R12 · P3293R3 · P3394R4 · P3795R2）GCC 列记 "16*"**，紧随其后的 **`<meta>`「Reflection library support」记 "16 (partial)*"**，同一行 Clang / MSVC 列为空。即"反射已进 C++26 且已有首个实现（库部分支持）"。因此 §3.3 的结论要补一个前提：反射可用后，"新增操作"可以由库按类型信息生成，Serialization / Visitor 族的形态会从"手写 `std::visit` 重载"部分转向"基于反射的通用序列化"；但各编译器进度不齐，两类写法定会在一个较长窗口内并存——**"最终形态"现在还不是单一形态**。判据（若要落成矩阵）：以该表 + 各编译器 release notes 逐版本核对，产出"最小可用版本 × 特性可用度"表。
> ① **仍开放**：模式使用率实证统计口径——判据=必须同时给出可复现的统计方法、数据集与样本量（在哪个 commit/如何识别一个模式实例/样本多大），三样缺一，"使用率"就只是印象而非统计。
> ③ **仍开放**：协程对 Callback/Observer 在 IO 层的替代进度——判据=选定一个具体 IO 层（如某个网络库）分别统计两类接口的出现频次与版本趋势，并把 C++20 协程库的采用情况单列，否则不可比。
