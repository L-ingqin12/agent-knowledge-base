# 操作系统实现视角：从引导到内核

> [!abstract] 定位
> [[操作系统八股]] 讲"是什么"，本文讲"怎么造出来"：加电→BIOS→MBR→loader→保护模式开启→GDT/特权级→时钟中断→C 内核→shell 的完整链路。每一步都回答"为什么必须有这一步"。硬件地基见 [[计算机组成原理]]，ELF 细节见 [[LibC与动态链接]]。

See also: [[CS-KB-Home]] · [[操作系统八股]] · [[计算机组成原理]] · [[LibC与动态链接]]

## 一、加电到 MBR：为什么第一段代码在 0x7C00

```
上电 → CPU 复位进入实模式, CS:IP = 0xF000:FFF0 (BIOS ROM 顶部)
     → BIOS POST 自检 → 按启动序读磁盘第一个扇区(512B)
     → 校验魔数 0x55AA(第510-511字节) → 装载到 0x7C00 → jmp 过去
```

**0x7C00 从哪来**：1981 年 IBM PC 把 BIOS 自身+中断向量表+BIOS 数据区规划在低端 32KB 之上——`0x8000 - 512B - 栈空间 ≈ 0x7C00`，纯历史布局沿用至今。MBR 只有 512 字节放不下完整加载器 → 职责仅一个：**把后续 loader 从磁盘按 CHS/LBA 读进内存再跳过去**（分块读=突破单扇区限制）。

实模式编程要点（历史兼容知识）：20 位地址=`段<<4+偏移`；默认段约定（CS:IP / SS:SP / DS:数据）决定为什么 `rep movsb` 前必须先设 DS:SI、ES:DI——ES 可自由设而 DS 受指令默认约束。

## 二、开启保护模式：三步仪式

```
1. 关中断 cli + 开 A20 地址线(突破第21根线被屏蔽的历史兼容, 否则奇偶环绕)
2. 加载 GDT: lgdt [gdt_descriptor]      ← 段描述符表: 基址/界限/属性(DPL 等)
3. 置 CR0.PE=1 → far jump 刷新 CS 流水线, 进入 32 位保护模式
```

**A20 的三种开法**（内核 `arch/x86/boot/a20.c` 按序逐种尝试，每种开完都用 `a20_test_short()` 回环自证，整轮重试 `A20_ENABLE_LOOPS=255` 次）：
1. BIOS 法：`int 0x15, AX=0x2401`
2. 键盘控制器法：`outb(0xd1, 0x64)`（Command write）+ `outb(0xdf, 0x60)`（A20 on），每步之间 `empty_8042()` 等 8042 就绪（另有 0xff/0x64 null command）
3. Fast A20：操作 0x92 端口，置 0x02 并清 0x01——内核注释逐字写着「Do not reset machine」

**怎么验证**：开完做回环测试——往 `0000:0500` 与 `FFFF:0510` 写不同值再读回，能区分即 1MB 以上已可寻址；不通过就换下一种方法重试。

> 来源：https://raw.githubusercontent.com/torvalds/linux/master/arch/x86/boot/a20.c （`git.kernel.org` 的 `/tree/` 与 `/plain/` 链接在 2026-09-13 访问时返回 Anubis 反爬挑战页，内容经 GitHub 同源镜像核实）

**推理链**：为什么 far jump 是必需的？置 PE 后流水线里还缓存着实模式的段语义译码结果——跨段跳转让 CPU 以新段描述符语义重新取指。为什么需要 GDT？保护模式的"段寄存器"不再是裸基址而是**选择子**(索引 TI RPL)，真正的基址/权限在描述符表里——这是"保护"二字的第一层含义：访问越界/越权由硬件拒绝而非软件祈祷。

平坦模型：所有段基址 0、界限 4GB，分段名存实亡——现代 OS 一律平坦段+分页管地址；但 DPL 权限位仍在段选择子里工作。

## 三、特权级：ring0/ring3 与门

| 机制 | 作用 |
|------|------|
| CPL(当前)/DPL(目标)/RPL(请求) | 三级权限检查——用户代码(CPL3)访问内核段(DPL0)被硬件拒 |
| TSS | 任务状态段：ring3→ring0 时从 TSS 取 ring0 的 SS:ESP——**没有内核栈就没法安全执行内核代码** |
| 门描述符 | 系统调用门/中断门：唯一合法的降权→升权通道，入口受控 |

**系统调用的本质**就是一次经门的受控提权：用户态把参数放寄存器 → `int 0x80/syscall` → 硬件切到内核栈、CPL 变 0 → 内核函数执行 → `iret/sysret` 还原现场。理解了门，"为什么用户程序不能直接碰网卡寄存器"这类问题自动消解——IO 敏感指令在 CPL3 下触发异常。

## 四、中断与时钟：抢占的物理基础

```
8259A PIC 初始化(ICW 屏蔽字/EOI) → 时钟芯片 8253/HPET 定时发 IRQ0
IDT(中断描述符表) 注册 handler → 时钟中断每 tick:
    保存被打断上下文 → 更新系统滴答 → 当前进程时间片-1 → 归零则调度切换
```

这就是 [[操作系统八股]] "时间片轮转"的物理真相：**并发感来自定时器硬件周期性打断一切**。缺页异常(#PF)也走同一条 IDT 通路——错误码给出"缺在哪类页"，内核据此走 COW 分配或换页（对照 §六 缺页三类型）。APIC 替代 8259A 后多核路由更精细（x2APIC/**待确认**各代变化），机制不变。

## 五、用 C 写内核：ELF 加载与栈规划

```
loader 的最后一件事: 解析 kernel ELF 头(Program Header)
   → 按 p_vaddr 把各 LOAD 段搬到应许位置(.text 只读/.data 可写/.bss 清零)
   → 规划内核栈(通常紧邻内核高端) → e_entry 跳入
```

- **为什么内核不能依赖运行时**：此刻没有 libc——printf 得自己写（直接写 VGA 文本缓冲**物理地址 0xB8000**——等价段式写法 `B800:0000`，每字符 2 字节：低字节字符码、高字节属性；单色模式基址为 0xB0000（内核 `vgacon.c` 的 Monochrome 分支）；或走串口）；这也是 freestanding 编译(`-ffreestanding -nostdlib`)存在的原因。[[LibC与动态链接]] 讲的"C 库建立在 OS 之上"在此处得到字面证明
- C 与汇编交界：入口 stub(osKernel.asm) 设置好栈指针再 call c_kernel——**C 函数假设的一切调用约定前提由汇编负责建立**
- bochs/QEMU+GDB remote 调试是开发期主战场：断点打在物理地址，观察 GDT/CR0/寄存器逐项验证

> [!warning] 更正（2026-09-13）：文本缓冲区的基址是**物理地址 0xB8000**，`0xB800` 只是段式写法 `B800:0000` 的段值——按物理地址写 0xB800 会落到错误位置。（原表述为「直接写 VGA 文本缓冲 0xB800 或串口」）
> 来源：https://raw.githubusercontent.com/torvalds/linux/master/drivers/video/console/vgacon.c

## 六、Tiny shell 的完成度清单（自研最小闭环）

| 部件 | 最小实现要点 |
|------|-------------|
| 输入回显 | 键盘中断(IRQ1)→扫描码转 ASCII→环形缓冲→readline |
| 命令分发 | 字符串比较表驱动：clear/help/time/poweroff——数据驱动优于 if 瀑布([[设计模式实战]] 命令表思想) |
| 清屏 | 重置 VGA 光标位置+填空白字符属性字节 |
| 关机 | 向 ACPI/QEMU isa-debug-exit 端口写约定值(虚拟化环境) |

**完成这个闭环后回头看 Linux**：boot→init 进程→syscall 表→调度器 tick→shell，结构完全同构，只是每个部件放大了一百倍加了 SMP/NUMA/MMU 多级页表——八股里的抽象从此有了物理锚点。

## 七、待确认项

> ① UEFI 接替 Legacy BIOS 后本链路的变化面(GOP/Stub loader)；② x86-64 长模式下的同等实验(页表四级/GDT 必需性)差异清单；③ 各教学内核(Xv6/xv6-riscv)对多核启动(IPI)的处理深度。

> [!success] 残余复核（2026-09-13，联网核实）：② ③ 已可定论，① 仍开放。
> ② **已核（内核源码）**：长模式引导与 §二 的 32 位仪式**不同**——`arch/x86/boot/compressed/head_64.S`（torvalds/linux master，2026-09-13 抓取）里 `startup_32` 明确**仍要 `lgdt`** 载入"64bit segments using 32bit descriptor"（GDT 仍**必需**），随后 `CR4.PAE` → 手工搭 `pgtable`（PML4→PDPT→PD→PT 四级）→ 置 `_EFER_LME` → far jump `startup_64`；注释点明此时处于"32bit compatibility mode with EFER.LME = 1, CS.L = 0"，要靠新 GDT 里的 `__KERNEL_CS`（CS.L=1）才真正进长模式。差异清单即：多出 PAE/LME/CR3 三个开关、页表由"无分页"变为四级手工搭建、GDT 由"要建"变为"要换成 64 位描述符"。
> ③ **已核（两版 git 源码对照）**：xv6-riscv（`kernel/start.c`、`kernel/main.c`）与 xv6-public/x86（`lapic.c`、`main.c`）实取源码（2026-09-13 抓取）——**riscv 版全仓库无任何 IPI/软件中断发送**（`msip|send_ipi|softint` 零命中），多核启动靠 hart0 `__atomic_store_n(&started,1,RELEASE)` 与其余 hart 的 acquire 自旋；**x86 版**则完整实现 Intel「universal startup algorithm」：`lapicstartap()` 发 INIT(ASSERT)→INIT→**STARTUP IPI 连发两次**（源码注释原文 "Send startup IPI (twice!)"），另有 `lapicinit` 的 arbitration ID 同步广播。结论：教学内核的"多核深度"差异就是**有无 IPI**——riscv 版连核间中断型协作（如 TLB shootdown 广播）都不具备。

> [!warning] 残余复核（2026-09-13）：① 仍开放——UEFI 接替 Legacy BIOS 后的变化面，本机无 x86-64 UEFI 引导实验环境、库内亦无更权威口径。判据：抓 UEFI 规范的 GOP（Graphics Output Protocol）章节 + Linux `arch/x86/boot/compressed/` 的 EFI 入口（`efi_mixed.S` 与 stub 交接路径），核对着眼点是「谁提供帧缓冲（GOP vs VGA 文本缓冲 0xB8000）、谁做 Stub loader 交接、§二 的 A20/far-jump 仪式里哪些步骤被固件接管」。期望产出：一张"Legacy BIOS 链路 vs UEFI 链路"的逐步对照（每步标注由固件还是内核完成）。
